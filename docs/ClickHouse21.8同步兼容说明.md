# ClickHouse 21.8 同步兼容说明

## 本次修复

报错 `Unknown function serverUUID` 来自同步前的物理表身份检查。实测 ClickHouse 21.8.9.13 不提供该函数，不能直接调用。

现在先探测函数能力：支持时保留原实例 UUID 和锁名称；不支持时使用业务库的 Atomic UUID，Ordinary 库则使用可读取的 system 库 UUID。不会使用 IP、端口或主机名代替物理身份，也不会吞掉网络、权限异常后继续清表。

同表检测、目标锁、未完成任务占用、基线接管和断点保存共同使用这一身份规则。HTTP 与 native、不同连接账号指向同一表时仍会相互排斥；重建数据库会使旧身份失效。新增兼容锁写入现有 `el_sync_checkpoints.state_json`，不需要执行 MySQL DDL，不增加目标表业务字段。

## 支持范围

- **21.8.9.13 作为源库**：已实测 HTTP/native、Atomic/Ordinary 库及仅有业务表 SELECT 权限的 Atomic 源账号。源表仍须为独立 MergeTree 系列表。
- **旧版 Ordinary 源库**：账号还需要能看到 system 库的持久化 UUID。无法取得可信身份时明确报错，保留断点，不绕过同表保护。
- **25.3.14.14 作为目标库**：已验证实际写入、同一批次重试去重，以及不同批次相同业务行的正常写入。
- **21.8.9.13 作为目标库**：实测缺少 `insert_deduplication_token`，当前断点写入协议不支持。程序会在打开写入断点和采集大批源数据前明确提示；应选择支持该能力的目标库，例如内置 25.3。不能仅删除去重设置来宣称兼容，否则响应丢失后的重试可能重复写入。

## 发布与断点

需要重新构建并部署应用，之前生成的发行 ZIP 不会自动更新。无需删除任务或清空目标表。新代码可读取原有断点；若任务配置、表结构或实际目标已发生变化，原有保护仍然生效。

此次断点 JSON 增加了兼容锁属性。旧应用未必能解析新属性，不应在新版本写入断点后直接回退旧程序，或让不同应用版本混用元数据库。发布前停止旧应用并备份元数据库；回退时需要配套评估断点及目标写入状态，不能单独恢复旧断点覆盖后续写入记录。

## 验证记录（2026-11-17）

使用隔离的 ClickHouse 21.8.9.13、25.3.14.14 和 MySQL 8.0.46，执行了 40 项实库检查，覆盖两种协议、只读账号、同表阻止、建表前后锁一致性、数据库重建、未完成断点互斥、锁丢失、基线状态替换、身份锁升级衔接，以及实际写入与重试。身份锁升级检查不代表允许跨 ClickHouse 版本重放未确认批次；原有写入版本检查仍保留。

Java 8 Maven 编译与打包通过。未向项目添加测试类。以上验证未连接生产数据库，也不替代生产网络、账号权限与实际任务配置的检查。
