# el-admin 库表权限修正记录

日期：2026-10-20。

## 当前规则

内置平台 `admin`（用户名、角色均为 admin）使用该 CK 实例配置的业务连接账号，当前部署预期是 `el-admin`。该账号已持有 `ods_data`、`dwd_data` 库内表的权限，页面不再按“本人或共享”额外隐藏其他用户创建的表。普通用户仍绑定 `el_user_<userId>`，只看自己的表及有效共享表。

这替代此前选择的“admin 与 user 也隔离”。其他被赋予平台 admin 角色的账号仍使用独立 CK 绑定，不因为角色变更自动获得 `el-admin` 身份。

## 原因与实现

此前有两处限制：内置 admin 被要求使用独立 `el_user_<ID>`，表列表又按平台所有者及共享关系过滤。因此 CK 连接账号拥有库级权限也无法在页面看到其他用户的表。

- 启动时核对内置 admin 的绑定，切换为该实例配置的业务连接账号并校验 `currentUser()`。凭据来自业务连接配置，不能回退到专用 CK 管理身份；绑定失败保留错误状态并允许重试。
- 管理员表列表、统计、结构、预览和读写按业务 CK 身份执行。列表合并平台元数据，保留原 owner、创建者和资产 ID；不会把其他用户的表变成 admin 所有。
- 对 CK 已存在但平台未登记的表，admin 能查看、读写，并在具备原生 DROP TABLE 权限时删除；创建者显示“创建者未知”，不自动登记或认领。此类表仍不提供依赖平台资产的共享、改名操作。
- 已登记资产的受控删除、改名前，通过业务连接执行 `CHECK GRANT` 检查所需权限，再处理平台资产和授权清理。参见 [ClickHouse CHECK GRANT 文档](https://clickhouse.com/docs/reference/statements/check-grant)。普通读写由业务连接执行，CK 继续决定是否允许。
- 配置账号不是平台生成的账号，其原生库级授权和默认角色不参与临时建表授权、所有者授权或资产清理。撤销共享不等于撤销 `el-admin` 原有库级权限。绑定停用时也保留这些外部账号的权限。
- 只有真实所有者能共享自己的表。普通用户共享后，对方在原列表看到创建者及只读权限；没有新增共享菜单，也没有恢复历史归属菜单。
- 数据源、上传文件、任务、工作流和 SQL 草稿继续按平台所有者隔离。平台账号管理仍只允许 admin 角色。

## 验证

使用一次性 MariaDB 10.11、ClickHouse 25.3.14.14、JDK 17 应用实例。CK 管理身份为临时 `default`；业务账号 `el-admin` 仅授予两个业务库权限。通过真实 HTTP 接口验证：

- admin 自动绑定 `el-admin`，SQL `currentUser()` 返回该账号；普通用户分别使用自己的 `el_user_<ID>`。
- 两个普通用户分别在两个库创建表，admin 无需共享即可列出、预览、查看结构和读写；列表保留原创建者。
- 两个普通用户看不到对方私有表，输入完整表名查询仍被 CK 拒绝。
- 未登记的物理表对 admin 可见且可读写，未伪造资产或创建者，普通用户不可见。
- 普通用户之间共享只读，INSERT 被拒绝，撤权后 SELECT 被拒绝。向 admin 共享再撤销不影响其原生库级权限。
- admin 建表、改名、删除自己或其他用户的已登记表后，`SHOW GRANTS FOR el-admin` 与验证前一致；改名保留原创建者，普通所有者仍能读取新表名。
- admin 绑定停用后，普通所有者删除曾共享给 admin 的表，`el-admin` 原生授权仍与验证前一致。
- 临时收回业务账号的 DROP TABLE 权限后，管理员受控删除返回 403，原表仍存在。
- admin 可访问平台用户管理接口，普通用户被拒绝。

现有后端 47 项测试、前端 463 项测试、类型检查和构建通过。临时验证脚本、专用容器和测试数据在完成后清理；保留原有测试文件，不提交新增测试代码。

## 未登记表删除补充修正

此前列表已允许显示未登记的 CK 表，但删除入口仍首先调用 `requireOwnedAsset`，没有资产记录就返回“表不存在或未登记”。这是删除路径未同步开放导致的错误，与物理表是否存在无关。

- 未登记表：只允许内置 admin 在配置的业务库内操作，校验原生 DROP TABLE 权限后，直接用当前业务账号执行精确 `DROP TABLE IF EXISTS ... SYNC`；不借管理账号代删，不临时认领资产，不修改库级授权。
- 已登记表：沿用所有者/管理员校验、撤权、物理删除和资产退役流程。普通用户不能删除未登记表，共享只读用户不能删除别人的表。
- 新增独立 `canDrop` 能力供删除按钮使用，不再将“没有资产管理能力”误判成“管理员不能删除物理表”。删除后失效当前用户的表统计缓存，并刷新列表与分组。
- 删除成功记录 `table.drop.unregistered` 审计，不虚构资产 ID；实际库表和执行账号可在 CK 查询日志核对。

补充使用一次性 MariaDB/CK 实测通过：两个业务库的未登记表均可删除；同名跨库表只删除请求的目标；重复删除幂等；列表和统计不再包含已删除表；不新增资产、不改变原生授权；CK 查询日志中的删除执行用户确认为 `el-admin`。撤销 DROP TABLE 后返回 403 且表仍存在；普通用户删除、共享用户删除及非业务库删除被拒绝；原有已登记表的删除和撤权清理仍正常。

新增 3 项前端临时回归测试通过：未登记表删除按钮和确认流程、只读/明确禁止时隐藏删除、未传可选能力参数的原调用方式兼容。验证完成后删除新增测试文件和临时数据库脚本，保留上述记录。

## 应用方式与范围

使用本次构建的后端 JAR 和 `web/dist`，重启应用并重新登录；无需重启 MySQL。确认运行配置的 CK 业务账号为持有这两个库权限的 `el-admin`，平台用户管理中 admin 的绑定应显示 `el-admin / active`。失败时在该页面查看原因并重试初始化。

本次仅修改工作区并在临时环境验证，没有连接或修改 212 数据库，没有改现有登录密码、CK 密码、真实库表授权，也没有替换或重启正在运行的部署服务。旧 `el_user_1` CK 账号不会自动删除。
