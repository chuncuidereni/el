# MySQL 按日期分表同步

仅影响选择了“按日期分表”的 MySQL 同步任务，原单表以及其他类型的数据源继续使用原逻辑。多个日期表按同一份字段映射写入一个 ClickHouse 目标表。

## 配置示例

在“映射同步 → 新建/编辑任务”中选择 MySQL 数据源，然后将“源表方式”设为“按日期分表”。

| 配置 | 示例 |
| --- | --- |
| 表名规则 | `xx_xx_{yyyyMMdd}`，也可使用 `business_db.xx_xx_{yyyyMMdd}` |
| 起始日期 | 可留空，不预填；例如 `20260101` |
| 结束日期 | 可留空；仅填开始日期时读取至执行时的业务当天 |
| 业务时区 | 默认 `Asia/Shanghai` |
| 分段键 | 各日表共有的整数单列主键，例如 `id` |

点击“预览匹配表”，读取现存表清单及第一张匹配表的参考结构，再配置字段映射。至少需要一张现存参考表才能保存任务。表名必须精确匹配规则；例如备份表 `xx_xx_20260101_bak` 不会被 `xx_xx_{yyyyMMdd}` 选中。只匹配基本表，不匹配视图。

新增和编辑页按基本信息、来源、目标、同步策略、执行设置分区。未选数据源时隐藏后续配置；只有 MySQL 日期分表展示表名规则与日期范围，只有分表增量展示新表策略。Hive、Kafka 不展示增量选项，SFTP 使用文件增量配置。更换数据源或源表会清理旧字段映射、分段键和手机号列；普通策略切换保留原配置以兼容已有断点。字段预览默认收起，定时配置仅在选择定时执行后显示。

表名规则默认为空，输入框提示 `如 xx_xx`，输入前缀后自动补齐 `_{yyyyMMdd}`。表名规则与日期区间放在同一行，开始与结束日期分别使用一个日期框，两者均不预填。全部清空表示“全部日期”。前端提交 8 位日期，后端也兼容 `2026-01-01` 格式。

| 开始日期 | 结束日期 | 读取范围 |
| --- | --- | --- |
| 空 | 空 | 所有名称匹配且日期有效的现存基本表，包括已存在的未来日期表 |
| 有值 | 空 | 开始日期至执行时的业务当天 |
| 有值 | 有值 | 指定区间；未来日期截止到业务当天 |
| 空 | 有值 | 不允许，提示先填写开始日期 |

如果开始日期为 `20260101`，执行时的业务日期为 2026-11-11，且结束日期留空，本次会发现 `20260101` 至 `20261111`（含两端）的现存表；不会提前读取未来日期的表。到次日执行时自动发现次日表。实际读取时间沿用任务的 Cron/定时调度设置，日期规则本身不新增定时器。填写日期范围时最多 3661 天。

## 全量与增量

- **全量**：默认在本轮首次写入前清空目标一次，再按日期合并所有匹配表；不会每读一张表就清空目标。关闭清空开关后，全量会追加全部数据，多轮执行会重复追加，这与单表全量相同。
- **增量**：新建日期分表任务的“发现新表”默认选择“完整导入”。首次从空目标读取各表的全部现存数据，后续执行分别从每张表自己的水位继续。新出现的日表从头读取，即使其主键重新从 1 开始，也不使用其他日表的水位过滤。历史日期中新建的表会在下次发现；旧表追加且超过该表水位的行也会补读。全量模式不展示新表策略。
- **仅接后续数据**：这是另一个显式选项，首次运行也不导入历史。时间型增量键从上次成功扫描的开始时间之后读取（首次用本轮开始时间）；数值键以新表发现时最大值为起点。早于上次扫描日期的新表会跳过。已有任务不因升级自动改变该策略。
- **全量切换增量**：保留原分表任务，等待全量成功后，将策略改成增量。页面自动清空结束日期、将增量键设为原分段主键，并默认完整导入后续新表；开始日期、来源、字段映射、批大小和目标配置保持不变。结束日期留空后，每次执行读取到业务当天并发现后续日期表。新表策略和定时设置可以调整。保存时先以原结束日期重算完整全量指纹，确认其他配置兼容，再将任务与已完成断点的配置指纹在同一 MySQL 事务中更新；更新失败一起回滚，逐表水位、已确认行数和目标身份保持原样。执行时再次校验目标身份。目标保留已有数据，各表从全量的已确认位置继续，不清空、不从源当前最大值重建起点。尚未运行过的任务可以直接改为增量，执行时要求目标为空。
- **推荐持续采集方式**：新建任务时直接选增量，并选择新表“完整导入”。这样首轮完成历史导入，之后按定时持续追加，无需先选全量再切换。预览会显示匹配表数和参考表主键，新增页面联动默认分段键及增量键。
- **重新传输**：使用已有的“重新传输”操作清空目标并重新建立全部分表基线；普通“执行”优先恢复失败轮次。

分段键必须是每张表共有的非空整数单列主键，目标映射保留原整数类型且不可空；手机号转换列不能作为分段键。增量键必须非空、持续递增。若增量键不同于主键，需要以“增量键、主键”为前两列的索引，读取时使用二元游标，避免同一时间值多行跨批次漏读。预览会尝试默认选择整数主键，保存与运行仍会校验。

增量是追加同步，不是 CDC：旧记录修改、删除或插入到已越过的水位之前，不会自动反映到目标。日表在同步及恢复期间应保留历史记录，不能删除、清空或重建后复用旧主键。检测到最大水位回退会停止，但不能据此证明源表所有历史数据未变化。

## 续传、进度与异常

每轮开始时冻结本轮范围内的匹配表清单；两端日期为空时使用全部匹配表。进入一张表时固定该表的读取上界，随后按批次直接读取、写入，不生成整表缓存文件。这是有界分批读取，不是所有日期表同一时刻的事务快照。

每张表的已确认水位、当前表、固定上界、待确认批次、写入去重令牌及完成状态都保存在 MySQL。跨表游标包含表名，不会因不同表主键相同而串用断点。目标确认写入后才提交水位；进程重启或写入响应丢失使用原批次与去重令牌恢复。未完成轮次先按原清单续传，成功后的下一轮才发现新表。

进度显示当前源表、已完成表数/总表数和已确认写入行数。表完成百分比不表示按行数完成的百分比，也不对所有大表先执行 `COUNT(*)`。没有查到匹配表时记录普通说明，保留目标，不执行清空。缺失日期下次重新发现，不会永久标记为已完成。

实际进入每张表时校验字段名称、顺序、类型及分段索引。不一致时明确失败并保留断点，不静默跳过该表。源表在本轮发现后被删除也会报错，不把删除解释为成功。

合并目标中无法可靠区分各日表相同的主键，因此分表任务不支持从目标最大值“接管已有全量数据”。需保留原任务的逐表断点，或通过明确的重新传输重建基线。改表名规则、日期范围、映射、分段键或增量键不能沿用不兼容的旧断点。

## 部署与存储

本功能不新增元数据库列或表，也不增加 ClickHouse 目标辅助字段：

- `el_sync_tasks.schema_json` 的 v3 对象保存 `mysqlDateTables` 与参考列结构；单表任务仍使用原 v2 格式。
- `el_sync_checkpoints.state_json` 保存逐表清单和水位。只保存游标与摘要，不存放业务行数据。
- 手动执行、定时执行、自动重试均经过同一同步引擎。

需重新打包前后端并部署后使用。本功能不涉及 SQL 结构升级；此前日志逻辑删除缺少 `el_sync_runs.deleted_at` 的问题仍需按 [元数据库说明](README.md) 执行对应升级。旧版程序不识别 v3 日期分表任务，不能让新旧应用同时运行同一任务。

接口：`POST /api/sync-tasks/mysql-date-tables/preview`，请求只需数据源 ID 和规则。创建/更新任务沿用现有接口，增加可选 `mysqlDateTables`，传 `null` 表示单表。

```json
{
  "dataSourceId": 1,
  "mysqlDateTables": {
    "tablePattern": "xx_xx_{yyyyMMdd}",
    "startDate": "20260101",
    "endDate": "20261231",
    "dateFormat": "yyyyMMdd",
    "timeZone": "Asia/Shanghai"
  }
}
```
