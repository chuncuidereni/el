## 1. 本轮已经完成

### 1.1 全仓注释覆盖与关键业务注释

本次已对实际参与运行、构建和部署的源文件补充中文维护注释：

- `src/main/java` 271 个 Java 文件：文件职责、公共类型/方法契约、参数与返回值、异常传播、权限、事务、并发和恢复边界。
- `src/test/java` 15 个测试文件：测试目标、前置条件与断言意图。
- `web/src` 124 个 Vue/TypeScript/CSS 文件：页面职责、响应式状态、请求生命周期、旧响应保护、卸载清理和类型契约。
- `src/main/resources/com/el2ck/mapper` 12 个 MyBatis XML：文件职责及动态 SQL 使用约束。
- Dockerfile、Compose、部署/打包脚本、Spring YAML 和关键前端构建配置：配置来源、安全边界、构建缓存、发布归档和回滚语义。

注释采用“文件职责 + 复杂分支说明 + 公共契约”的方式，没有给普通 getter、模板标签和显而易见语句逐行堆注释。MySQL 迁移 SQL 是 checksum 敏感文件，未改动其字节；`package.json`、`package-lock.json` 等不支持注释的格式保持原样。

注释重点放在状态机、失败恢复边界和“为什么必须按这个顺序执行”，没有逐行复述代码。主要覆盖：

- 同步断点：MySQL 命名锁、任务指纹、重试 token、pending 批次、恢复前校验、写入确认后推进水位。
- 同步执行：单 JVM 防重入、线程所有权、取消、进度节流、运行记录最终收尾。
- 分段读取：JDBC、ClickHouse、Kafka、SFTP 和快照来源的分段边界及可重放条件。
- ARB 工作流：固定快照、临时表、断点游标、原子发布、UUID 核对、失败恢复和命名锁。
- ClickHouse 客户端：`native/9000`、`native/9001`、`http/8123`、`http/8132` 的协议与端口配对，流式查询超时和批量 INSERT 分块边界。
- 前端：同步轮询、历史抽屉的旧响应保护、数据源删除关联校验、后台工作流观察器和组件卸载清理。
- Docker：配置来源、凭据隔离、Maven/npm 缓存、非 root 运行、健康检查含义、发布包白名单和原子替换。

后端关键文件已按“移除注释和空白后代码等价”逐文件核对；前端全量注释后通过 Vue TypeScript 类型检查。全仓最终复核结果见第 4 节。

### 1.2 部署与打包加固

- `.dockerignore` 现在排除所有 `src/main/resources/application*.yml`，防止本地 `application-test.yml` 中的连接凭据被打进镜像。
- Dockerfile 先复制 `pom.xml` 并预下载 Maven 依赖，再复制源码，源码变化时不再重复下载全部依赖。
- 生产镜像构建跳过测试编译，测试应在 CI 或发布前单独执行。
- 发布脚本只把部署所需文件列入必需清单。`tests`、`src/test`、`docker/mock-sources` 不再进入生产归档；`README.md` 和 `docs` 变为可选内容，删除它们不会导致打包报错。

- 容器配置补齐了 `app.arb-resume`、`spring.sql.init`、会话 Cookie 和日志线程名等主配置项，减少容器与本地配置漂移。

## 2. 高优先级问题

### 2.1 部署阻断：MySQL 结构迁移没有启动前校验

当前应用不再自动执行 MySQL 迁移，启动时也不会检查 `el_sync_checkpoints`、`el_arb_checkpoints`、`progress_json` 等新增结构。部署时漏执行手工 SQL，应用仍可能成功启动，直到第一次查询才报缺表或缺列。

处理建议：

1. 部署前必须执行对应的 `docs/mysql/*.sql`。
2. 增加启动前置检查，验证关键表、列和版本号。
3. 检查失败时终止启动，避免以“容器 healthy、业务不可用”的状态上线。

### 2.2 同步防重入只在单个 JVM 内有效

`SyncService` 的 `synchronized(gate)` 和“先查 running、再插入 running”只能约束同一个进程。两个应用实例可能同时查询到零条 running，然后分别启动同一任务，造成重复读取、重复写入和断点互相覆盖。

处理建议：在 MySQL 任务行上加锁，或增加 `running_owner_id` 等生成列和唯一索引，让防重入成为数据库级约束。

### 2.3 启动重置会误伤其他实例正在执行的任务

`resetInterrupted` 当前只按 `status='running'` 更新记录，没有实例 ID、心跳或租约。滚动发布、临时启动第二个容器时，新实例可能把旧实例仍在执行的任务改成失败。

处理建议：增加 `owner_instance_id`、`heartbeat_at`、`lease_expires_at`，只重置确认失联且租约过期的记录。

### 2.4 同步运行收尾写库失败后会永久停在 running

`finishSyncRun()` 重试后仍失败时只写 `stderr`。此时数据可能已经同步完成，但 MySQL 仍显示 running，并阻止下一次运行。

处理建议：结构化告警、本地补偿记录和租约恢复机制至少实现一种；不能静默降级为只打印日志。

### 2.5 ARB 自定义 WHERE 可在高权限连接下执行危险表达式

ARB 条件只禁止分号、注释和 `#`，没有限制 `UNION ALL`、子查询和 ClickHouse 表函数。该条件随后在工作流管理身份下拼接执行，拥有工作流编辑权限的用户可能借此读取其他表或调用高权限函数。

处理建议：使用表达式 AST 白名单，只允许源表列、常量、比较/逻辑运算和明确允许的函数；更彻底的做法是让实际执行使用受限 CK 用户。

### 2.6 前端工作流忙碌状态会互相覆盖

`ArbWorkflowsView.vue` 和 `DwdLayerView.vue` 用单个 `busyId` 表示正在执行的任务。工作流 A 运行时启动 B，B 会覆盖 A；任一任务完成后又会把忙碌状态清零，导致另一个仍在运行的工作流按钮重新可点。

处理建议：改为 `Set<number>`，按工作流 ID 判断禁用；或者在入口明确禁止页面内并发执行。

### 2.7 删除分组会忽略成员删除失败

选择“同时删除成员”时，前端逐条删除并吞掉单条失败。某个数据源被同步任务引用而删除失败后，分组仍会被删除，页面还可能提示“已删除分组及其成员”。

处理建议：收集失败项；只要有关联任务导致失败，就停止删除分组，并列出具体数据源和“请先删除关联同步任务”。

### 2.8 后台任务失败提示被抑制或缺失

- ARB 页面通过 `!e?.taskFailed` 阻止失败提示。
- 同步任务只对 success 弹提示，最终 failed 时没有展示后端错误。

处理建议：任务结束时展示 `run.error`，并提供“查看执行历史”入口；取消、进程中断和业务失败使用不同文案。

### 2.9 同步轮询可能永久吞错

除 404 回退外，同步状态查询和列表查询错误可能被静默吞掉。401 还是 silent 请求，不会触发登录跳转。页面会每 2 秒持续请求，并一直显示运行中。

处理建议：区分可重试错误和终止错误。只对网络错误、超时和 5xx 做有限次数退避；400/401/403/404/422 应终止轮询、清理 `runningIds` 并显示错误或跳转登录。

### 2.10 当前整仓仍有 12 个既有编译签名错误

本轮注释修改没有改变业务逻辑，但静态核对调用点和声明后，工作区仍存在 12 个会阻断完整 Maven 编译的既有符号或方法签名不一致：

- `ArbResumableEngine` 有 4 处调用不存在的 `CkIdentityService.workflowManagementConfig(long)`。
- 同步分段读取路径有 4 处调用不存在的 `DbSource.validateSegmentKey(...)`、`openSegmentConnection(...)` 或 `readSegment(...)`。
- `SyncEngine` 有 2 处调用不存在的 `KafkaSnapshot.scannedOffsets()` 和 `totalOffsets()`。
- `SnapshotSources` 调用 `BigDataSource.hive(cfg, timeoutMillis)`，但当前声明只接收一个参数。
- `SyncTaskController` 调用不存在的 `SyncService.runLogs(...)`。

处理建议：先统一接口声明和调用方，再执行 Maven 编译与后端测试。不能用注释或关闭编译检查掩盖这些签名错误。

## 3. 中优先级问题

- `CkClient` 在 `secure=true + native` 建连失败的部分路径中可能没有关闭 `NativeTlsTunnel`，隧道线程会阻塞在 `accept()` 直到进程退出。
- 同步取消接口只设置线程中断，长时间阻塞的 CK 调用可能继续执行；接口应立即表达“取消请求已提交”，最终以运行状态确认。
- `ArbWorkflowService` 后台线程只捕获 `RuntimeException`，`Error` 可能绕过 `failIfRunning()`，让运行记录停在 running。
- ARB 把进度文本写进运行历史的 `sql` 字段，会污染 SQL 展示和审计；应增加独立 `progress/note` 字段。
- `SyncEngine` 当前先无条件设置 `resumable=true`，紧接着的普通进度上报条件不可达，属于需要清理的死代码。
- `MetadataSqlDialect` 的逻辑表名映射与手工 SQL 双维护，新增表或列时容易漏改，建议增加启动校验或离线一致性测试。
- 前端批量删除没有复用单条删除的关联任务提示，可能连续弹多个全局错误，却无法告诉用户具体失败的数据源。
- `loadRunLogs` 缺少 catch，失败时可能产生未处理 Promise rejection。
- 历史抽屉保存的是打开时的任务快照，断点字段更新后，运行确认文案可能仍显示旧值。
- `stableKey` 当前 UI 标为可选，也没有提交前校验；但测试要求必选。必须先确定后端契约，再统一 UI、测试和校验，不能在缺少业务决策时擅自改动。
- Docker 健康检查 `/api/health` 只是进程存活检查，MySQL 或 ClickHouse 不可达时仍可能显示 healthy。
- 命名卷如果曾被 root 镜像写入，新 UID `10001` 可能没有写权限；升级时需要一次性检查并修复卷属主。
- 发布流程尚未在 `deploy.sh` 内自动校验 SHA-256，也没有数据库预检、旧镜像记录和正式 rollback 动作。
- `JAVA_TOOL_OPTIONS` 固定 `-Xmx2g`，Compose 没有内存上限，需要按 212 的实际内存调整。
- Windows 不能可靠设置 NTFS 文件的 POSIX `0600` 位。上传 Linux 服务器后应执行 `chmod 600`，不要依赖 Windows 本地显示的外层归档权限。

## 6. 结论

当前代码在时间精度、CK 25.3 视图 COMMENT 顺序、四种 CK 协议/端口组合、断点两阶段恢复和 ARB UUID 发布路径上已有合理实现。部署链路的本轮加固解决了凭据入镜像、归档过宽、无关目录阻断打包和 `restart` 不加载新环境等直接问题。

生产上线前仍应先解决 MySQL 结构校验、跨实例同步防重入、运行状态租约和 ARB 条件表达式权限边界。前端至少应先修复并发忙碌状态、删除失败提示和永久轮询问题，否则在多人使用或后台失败时容易出现重复操作和状态误判。
