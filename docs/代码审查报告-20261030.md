## 1. 删除数据源时全表锁 `el_sync_tasks`

**位置**：`src/main/resources/com/el2ck/mapper/sync/SyncTaskMapper.xml:21`

```sql
SELECT id FROM sync_tasks WHERE data_source_id=#{sourceId} LIMIT 1 FOR UPDATE
```

**问题**：`el_sync_tasks` 的定义（`docs/mysql/archive/V1__metadata.sql:62-96`）只有 `PRIMARY KEY (id)`，`data_source_id` 没有索引，后续脚本也没有补。

**触发与影响**：MySQL 下该语句只能全表扫描，并对扫描到的每一行和间隙加 X/next-key 锁。删除一个数据源的事务提交前：

- 其他数据源删除会互相阻塞；
- 所有同步任务的新建、编辑、删除（写入 `el_sync_tasks`）都会被阻塞；
- 任务量大时，锁等待会直接表现为接口超时。

**验证方式**：

```sql
SHOW INDEX FROM el_sync_tasks;
-- 只有 PRIMARY，没有 data_source_id 相关索引
```

**建议方向**：补 `data_source_id` 索引（随 `docs/mysql/` 手工脚本发布），或在删除前用不加锁的查询定位候选行、只对命中的任务行加锁。

## 2. 一条坏配置让所有「连接删除」返回 400

**位置**：`src/main/java/com/el2ck/repository/metadata/MetadataRepository.java:585-597`

```java
if (node.isObject() && node.has(key)) {
    try { if (Long.parseLong(node.get(key).asText()) == id) return true; }
    catch (NumberFormatException e) {
        throw com.el2ck.exception.ApiException.validation("无法检查配置引用，" + key + " 不合法");
    }
}
```

**问题**：`containsReference` 现在遇到非数字值直接抛业务异常，而它被多处复用：

- `deleteConnection`（`MetadataRepository.java:431-447`）：`query_workflows.config_json`、`wide_table_tasks.config_json`、`sql_queries.visual_config`、`wf_tasks.nodes_json`；
- `deleteDataSource`（`:531`）：工作流 `nodes_json`。

**触发与影响**：历史数据里只要有一条配置含 `"connectionId": ""`、`"connectionId": null` 或 `"connectionId": "abc"`，删除**任意**连接（哪怕与那条配置无关）都会返回 400「无法检查配置引用，connectionId 不合法」，必须手工修好那条历史配置才能继续。数据源删除同理（`dataSourceId`）。

**建议方向**：引用检查对坏值应“跳过并记录/提示”，而不是让整个删除失败；加锁路径可以严格，删除检查不宜因无关脏数据阻塞。

## 3. 删除数据源时锁全表 `el_wf_tasks`

**位置**：`src/main/resources/com/el2ck/mapper/workflow/WorkflowMapper.xml:21`

```sql
SELECT id, nodes_json FROM wf_tasks ORDER BY id FOR UPDATE
```

**问题**：无条件对整表加锁，只为拿到“最新读”来检查引用。

**触发与影响**：REPEATABLE READ 下这是全表 next-key lock：

- 删除任意数据源期间，所有用户的 `createWorkflow` / `updateWorkflow` / `deleteWorkflow` 全部阻塞；
- 锁内把全部工作流的 `nodes_json` 读进内存，工作流多时内存与持锁时间都会放大；
- 与第 1 条叠加，两个表同时被锁，删除数据源成为一个长事务。

**建议方向**：引用关系应可索引查询（归一化的引用表，或在 `nodes_json` 上维护可查的 `data_source_id` 列），只锁相关行；`createWorkflow`/`updateWorkflow` 已对引用的源行加锁，可以覆盖“新增引用”的并发，不需要用整表锁来换取一致性读。

## 4. 工作流 ID 解析规则与保存校验不一致

**位置**：`src/main/java/com/el2ck/repository/metadata/MetadataRepository.java:570-574`

```java
if (node.isObject() && node.has("dataSourceId")) ids.add(Long.parseLong(node.get("dataSourceId").asText()));
```

对比 `WorkflowService.validate`（`WorkflowService.java:225-228`）使用的是 `cfgInt(...)`：接受 `Number`，对字符串会 `trim` 后再解析。

**触发与影响**：

- `"dataSourceId": " 1"`（带空格）能通过 `validate`，但在 `lockWorkflowSources` 里抛 `NumberFormatException`，被包装成「工作流数据源引用不合法」，工作流保存失败；
- 任何节点配置里带了一个非数字的 `dataSourceId` 键（例如某些模板/过滤节点残留），整个工作流会**永久无法保存**；
- 反过来，校验阶段已经拒绝的 `0`/负数，加锁阶段却会尝试锁定不存在的行并报「数据源不存在或无权访问」，错误信息与真实原因不符。

**建议方向**：两处共用同一个解析函数（同一套 trim/Number/null 规则），并把「解析失败」归到保存校验阶段，给出字段级提示。

## 5. 编辑任务时持执行锁做远程探测

**位置**：`src/main/java/com/el2ck/service/sync/SyncService.java:547-558`

```java
try (SyncExecutionGuard.Lease lease = executionGuard.reserve(id)) {
    SyncTask old = requireTask(id);
    validate(in);                       // 远程读源表结构、探测目标 CK
    checkTargetOwner(...);
    ...
}
```

**问题**：`validate` 内部会调用 `validateSourceColumns` → `describeCkSource` / `dataSourceService.sourceColumns`，以及目标归属校验里的物理表探测，都是远程调用；这些全部发生在任务级执行锁内。

**触发与影响**：源库或 ClickHouse 响应慢时，命名锁被长时间占用。此时该任务的定时触发拿不到锁，会被跳过并记录「任务未启动」，直到下一个 cron 周期；用户侧表现为“编辑一次任务，定时任务漏跑一轮”。

**建议方向**：锁外完成远程校验，锁内只做“重新读取任务 + 写库”这一段；或对远程校验结果做短 TTL 缓存。

## 7. `TreeSet` 先抛 NPE，`id == null` 校验不可达

**位置**：`src/main/java/com/el2ck/repository/metadata/MetadataRepository.java:554-556`

```java
for (Long id : new java.util.TreeSet<>(ids)) {
    if (id == null || id <= 0 || datasources.lockOwnedById(id, ownerId) == null)
        throw ApiException.notFound("数据源不存在或无权访问");
}
```

**问题**：`TreeSet` 使用自然排序，构造时会先 `add(null)` 抛 `NullPointerException`，下一行的 `id == null` 分支永远走不到。

**触发与影响**：一旦未来调用方传入含 `null` 的集合（例如可空的 `Long getDataSourceId()`），用户会看到 500，而不是预期的 404 提示。

**建议方向**：先过滤/校验再排序，或改用 `stream().filter(Objects::nonNull)` 后再收集。

## 8. `hasRunningSyncRun` 已成死代码

**位置**：`src/main/java/com/el2ck/service/sync/SyncService.java:709`

```java
if (repository.hasRunningSyncRun(taskId)) {
    throw ApiException.validation("任务正在运行中,请等待完成");
}
```

**问题**：`executionGuard.reserve(taskId)` 内部先执行 `recover()`（`SyncExecutionGuard.java:53-60`），把该任务所有 `running` 记录置为 `failed`。因此走到这里时计数恒为 0，分支不可能触发。

**触发与影响**：当前功能由命名锁保证，不会出错；但这段检查会让人误以为还有一层防重入保护。如果将来 `recover()` 被短路或调整，防重入会静默失效，而代码看起来仍有保护。

**建议方向**：删除该死分支，或改为断言/日志，明确“防重入由执行锁保证”。

## 10. Mapper 里写了物理表名 `el_` 前缀

**位置**：`src/main/resources/com/el2ck/mapper/datasource/DataSourceMapper.xml:26`

```sql
SELECT d.id FROM data_sources d
JOIN el_resource_owners o ON o.resource_type='datasource' AND o.resource_id=d.id
WHERE d.id=#{id} AND o.owner_user_id=#{ownerId}
FOR UPDATE
```

**问题**：该 Mapper 文件头注释明确要求“表名写逻辑名，执行时由 `MetadataSqlDialect.mysql()` 改写，不要自己写 `el_` 前缀”。这里直接写死 `el_resource_owners`，绕过了方言层。

**触发与影响**：目前能工作，只是因为 `resource_owners` 没有登记在 `MetadataSqlDialect.TABLES`。一旦该表被登记或方言改写规则调整，这条 JOIN 会指向错误/不存在的表，且没有编译期信号。

**建议方向**：统一写逻辑名 `resource_owners`，或把该表登记进方言表清单并去掉硬编码前缀（两者选一，保持全仓一致）。
