**1. [P1] MySQL 分段增量会静默跳过 NULL 水位行**

位置：[JdbcSegmentReader.java:108](../src/main/java/com/el2ck/sync/JdbcSegmentReader.java#L108)、[JdbcSegmentReader.java:132](../src/main/java/com/el2ck/sync/JdbcSegmentReader.java#L132)、[DbSource.java:184](../src/main/java/com/el2ck/service/datasource/DbSource.java#L184)。

触发条件：MySQL 源选择整数主键作为分段键，另一个可空字段（例如 `updated_at`）作为增量水位；主键和复合索引检查通过，目标映射设置为不可空。

源结构读取只保留类型，不传递 JDBC 的 `isNullable`。分段读取器检查的是目标映射的 nullable 标记，没有拒绝源水位的可空定义。读取 SQL 仅包含水位大小比较；`updated_at IS NULL` 的行根本到不了 `cursor()` 的空值检查。只要存在正常的非空水位行，MySQL 可以选出非空上界并完成其余行的同步，最后把任务标记成功。

示例：源有 `(1,NULL)`、`(2,10:00:00)`、`(3,10:00:01)`，现有边界条件只读取后两行，第一行没有报错，也没有进入目标。快照读取路径则保留 NULL 行并报错，两条路径行为不一致。

建议：保存和执行时都验证源水位的非空约束；对于必须接入可空列的任务，显式探测 NULL 并报出可处理的错误，不能默默过滤。可以复用诊断模块已经读取的 nullable 元数据，但不能只依赖用户是否运行诊断命令。

验证：使用内存 SQLite 对与当前代码相同的 SQL 谓词进行演示，3 行中只选出 ID 2、3；同时追踪保存、源类型读取、索引检查及分段执行路径，未发现运行时源 NULL 校验。此验证不是 MySQL 集成测试，也不证明线上任务已发生漏行。

修复：`DbSource.validateSegmentKey` 对 MySQL/PostgreSQL 的复合水位增加源列非空约束检查；`SyncService` 保存和 `SyncEngine` 执行复用该检查。通过 `LIMIT 0` 读取元数据，避免大表 COUNT 或扫描。源列允许 NULL 或无法确认约束时直接拒绝，即使当前没有 NULL 行也不能通过；提示补齐空值并设为 `NOT NULL`，或使用已有非空水位列。水位就是主键时沿用主键约束。程序不自动更改源表或目标字段。

**2. [P1] 重新传输保存新断点后，旧写入令牌会丢失**

位置：[SyncCheckpointStore.java:158](../src/main/java/com/el2ck/sync/SyncCheckpointStore.java#L158)、[SyncEngine.java:615](../src/main/java/com/el2ck/sync/SyncEngine.java#L615)、[SyncBatchWriter.java:56](../src/main/java/com/el2ck/sync/SyncBatchWriter.java#L56)、[SyncEngine.java:844](../src/main/java/com/el2ck/sync/SyncEngine.java#L844)。

触发条件：旧轮次有未确认 INSERT，用户选择重新传输；新轮次第一次保存之后、旧轮次 `stopCheckpointWrites` 之前，发生网络错误、自动重试或进程退出。

`open(restart=true)` 只把旧令牌和待确认标记放在 Session 内存字段 `previousToken/previousPending`，随后创建新 State。快照路径在读取源之前就保存新 State，其他路径也会在配置去重时保存；真正终止旧写入发生在后面的写入阶段。新 State 覆盖数据库后，旧令牌没有持久化副本。重试只能读到新轮次，无法再定位可能仍在 ClickHouse 执行的旧 INSERT。

后果：如果旧 INSERT 仍在服务端运行，它可能与新一轮清表、写入交错；现有“先确认旧写入停止，再重建目标”的保证不成立。

建议：在 MySQL 保存待终止的旧轮次令牌及清理状态；确认终止成功后再清除此状态，并允许清理动作自身恢复。另一种方式是在覆盖旧断点前完成可靠终止，但也必须处理终止响应丢失。无需添加目标表字段。

验证：临时编译当前 `SyncCheckpointStore` 和 `MysqlNamedLock`，用内存 JDBC 代理调用真实的 `open/save/open` 方法。输出如下；临时文件已自动清理，没有创建仓库测试类，也没有访问数据库：

```text
restart initially knows old pending: true
persisted state retains old token: false
retry remembers previous pending: false
retry remembers previous token: false
```

该验证直接确认令牌丢失；没有在线上模拟旧 INSERT 与 TRUNCATE 的竞争。

修复：将 `pendingStopTokens` 存入原有 `state_json`。新断点先保留旧令牌，执行终止并确认后再逐个清除；全部同步源入口都在新轮次采集和目标操作前执行该流程。停止失败和连续重传保留未完成义务，确认落库响应丢失时重新读取数据库决定是否重复幂等终止。同一目标的其他任务、接管基线和完成确认也受此状态保护。旧写入尚未停止时要求原配置指纹及目标锁一致，避免同主机不同端口误判为同一实例。无需新增 MySQL 表、字段或 ClickHouse 技术列。

**3. [P1] 页面设置 0 不限时，源读取仍有固定超时**

位置：[SnapshotSources.java:72](../src/main/java/com/el2ck/sync/SnapshotSources.java#L72)、[JdbcSegmentReader.java:44](../src/main/java/com/el2ck/sync/JdbcSegmentReader.java#L44)、[DbSource.java:47](../src/main/java/com/el2ck/service/datasource/DbSource.java#L47)、[CkRowSegmentReader.java:24](../src/main/java/com/el2ck/sync/CkRowSegmentReader.java#L24)。

页面和任务总超时已支持 0，但 JDBC 快照及分段读取把 0 改成 1800 秒，底层语句超时也限制为最多 1800 秒；ClickHouse 非唯一键全量分页的 SQL 则固定带 `max_execution_time=60`，不读取任务设置。

因此“任务总超时关闭”并不等于长时间源查询可以完成。单次慢查询仍可能被终止；在快照采集尚未完成的情况下，下一次尝试会从头采集，容易重现“读了很多行，确认写入仍为 0”。这不是说所有运行超过 30 分钟的任务都会失败：实际触发取决于单次查询耗时及 JDBC 驱动行为。

建议：明确区分连接超时、无响应超时、单查询超时和任务总超时。任务选择不限时后，长查询不能再隐式套用 30 分钟上限；分页读取需要独立限制时，应配置化并给出准确提示，避免把确定性超时当瞬时故障反复重试。

验证：追踪页面设置、任务定时器、两类 JDBC 读取和 ClickHouse 分页生成的 SQL。未运行耗时 30 分钟的查询验证。

修复：JDBC 分段和 JDBC/Hive 快照将 0 原样传给语句超时，非零值使用任务分钟数换算，不再限制为 1800 秒；Hive 正数 socket 超时也不再被截断。ClickHouse 行值分页的数据查询、上界和分页计划使用任务对应的 `max_execution_time`，取消固定 60 秒。连接探测、元数据、估算及网络读空闲保护独立保留：不限时 JDBC/Hive 任务仍有 1805 秒无响应限制，因此不能把 0 理解为任何网络状态下都无限等待。

**4. [P2] 已有目标的写入前置检查发生在整轮快照采集之后**

位置：[SyncEngine.java:608](../src/main/java/com/el2ck/sync/SyncEngine.java#L608)、[SyncEngine.java:616](../src/main/java/com/el2ck/sync/SyncEngine.java#L616)、[SyncEngine.java:829](../src/main/java/com/el2ck/sync/SyncEngine.java#L829)。

快照任务只提前检查有没有增量起点，随后采集完整快照；目标引擎、依赖视图、去重能力及目标身份等检查要等到 `transferCheckpointed` 才执行。已有可信增量起点时，前面的检查直接通过。

例如任务目标存在物化视图依赖，即使这一条件在开始时就可确定，程序仍可能下载大量源数据后才报“目标表存在依赖视图”。这与此前任务 18 的报错路径一致，也会浪费缓存空间。

建议：对已存在的目标，在采集源数据前做一次只读兼容性预检；正式写入前保留复检，避免采集期间目标变化。对于新建目标，提前检查能确定的配置和权限。不能简单删除视图保护来绕过错误；当前写入协议尚不能保证带副作用视图的重试一致性。

修复：快照入口在打开源、创建缓存及采集数据前，只读检查已有目标的引擎、依赖视图、同步 INSERT、目标身份、映射结构、去重配置及本轮所需权限。去重设置与实际写入共用判断；已经初始化的轮次不重新要求清表权限，已有足够去重窗口时不额外要求设置流程权限。新目标提前检查自动建表开关、目标库和同步 INSERT 设置；建表仍由原有受控流程执行。正式写入前复检，预检不建表、不清表、不修改目标列。

**5. [P2] 快照哈希清单造成大量重复元数据写入**

位置：[SnapshotSegmentReader.java:106](../src/main/java/com/el2ck/sync/SnapshotSegmentReader.java#L106)、[SyncCheckpointStore.java:279](../src/main/java/com/el2ck/sync/SyncCheckpointStore.java#L279)、[SyncBatchWriter.java:125](../src/main/java/com/el2ck/sync/SyncBatchWriter.java#L125)。

每采集一页就增加一个 64 字符哈希，然后序列化和 UPDATE 整个 State。清单增长后，之前所有哈希被反复重写。采集完成进入写入阶段，保存 pending、子批次摘要、子批次成功位置、整批确认时仍然携带完整清单。

按 132,440,000 行、每批 10,000 行计算，共 13,244 页；最终哈希数组约 0.846 MiB。仅数组部分的累计序列化量：采集阶段约 5.47 GiB，写入阶段按每页只有一条 INSERT、4 次保存计算又约 43.78 GiB。这里尚未包含其他字段、重试和额外子批次。

以上是代码路径推导的 JSON 数据量，不是实测磁盘占用，不能直接认定为服务器 55 GB 或 444 GB 的成因。但可以确认断点持久化本身存在明显写放大；缩小批次会进一步放大它。

建议：将不可变的快照清单独立保存到 MySQL 元数据表或受校验的清单文件，运行断点只更新游标、当前批次及清单标识。保持持久化顺序和摘要校验，不通过减少必要确认来换速度。

修复：逐页摘要保存为本轮缓存目录的 `snapshot-manifest.sha256`，MySQL 只记录 `snapshotPageCount`、`snapshotManifestHash` 和运行游标。先刷盘数据页，再追加并刷盘摘要，最后保存断点；完整 EOF 后才发布清单总摘要及完成标记。写入阶段不再重复上传完整哈希数组。旧完整快照首次恢复时把原数组迁移到独立清单，确认落库后清空旧数组；仍校验清单长度、总摘要及每个待写页，不重新采集有效快照。

**6. [P2] 重采快照会遗留已经不在清单中的尾页**

位置：[SnapshotSegmentReader.java:42](../src/main/java/com/el2ck/sync/SnapshotSegmentReader.java#L42)、[SnapshotSegmentReader.java:102](../src/main/java/com/el2ck/sync/SnapshotSegmentReader.java#L102)、[SyncCacheCleanup.java:194](../src/main/java/com/el2ck/sync/SyncCacheCleanup.java#L194)。

采集未完成时重试，会清空哈希列表、把页序号重新置零，但仍使用同一个 token 的缓存目录。代码只覆盖重新写到的页，没有删除旧清单的尾部文件。如果第一次采集了很多页，第二次很早失败，旧尾页仍留在磁盘。

清理器对未完成任务保留整个当前 token 目录，因此不会清理这些已不被新清单引用的文件。任务最终成功、删除或更换轮次后可以清理，但任务持续失败时，失效尾页会长期占用空间。

建议：在持有任务锁及缓存锁、确认尚无目标写入的前提下，对重采使用的页文件做明确重置，或给每次采集单独的代次；不能清理完整快照中待续传的有效页。

验证：临时目录演示“先写 5 页，再从第 0 页覆盖 2 页”的文件行为，目录仍有 5 页，其中 3 页已不在新清单中。结合清理器保留条件核对；未删除业务缓存。

修复：未完成采集重新执行时，持任务锁、断点锁和缓存锁，确认没有完整快照、目标初始化、已确认行数、待确认操作或待停止写入，再删除该轮失效分页及清单，随后才重新连接源。每个文件删除前复核锁，拒绝非普通文件；保留 SFTP 原文件及下载断点，包含保留编号 `file-2147483647.json`。完整快照和已经开始入库的轮次不走此清理路径；后台完成清理也已识别新清单文件。

**7. [P2] 并发满额会丢弃本次定时触发**

位置：[SyncService.java:764](../src/main/java/com/el2ck/service/sync/SyncService.java#L764)、[ScheduledSyncRunner.java:162](../src/main/java/com/el2ck/service/sync/ScheduledSyncRunner.java#L162)。

应用内 Cron 多个任务同时到点时，前三个占满名额后，后续任务启动直接抛错。定时器只记录日志并计算下一次 Cron，没有持久化待执行队列，也没有对应的失败运行记录。每天执行一次的任务可能整天未执行；运行数超过 3 的耗时任务组合还可能反复挤掉同一任务。

这是当前明确实现的调度行为，属于需要补齐的调度可靠性问题；不表示已启动任务会丢失断点。本结论针对应用内定时器，XXL-JOB 的重试行为取决于调度中心配置。

建议：将到期运行请求持久化排队，容量释放后再启动；同一任务的等待请求需合并或明确保留策略，并在页面展示“等待执行”。保留同任务和同目标表的互斥保护。

修复：应用内 Cron 先向既有 `el_sync_runs` 保存 `queued` 请求；派发器约每 5 秒尝试领取，有执行名额且取得任务锁后才把原记录改为 `running`。同任务最多保留一个等待请求，等待期间的触发合并并保存最晚已覆盖触发时刻，避免迟到回调重复入队。入队写库失败重试同一触发；进度上报、正常收尾和补偿收尾均保留触发去重信息。排队不占执行名额，已落库请求可跨重启恢复。任务编辑与取消旧排队在同一事务中提交；停用、删除或手动取消也会处理等待请求。页面显示等待状态及取消入口，当前运行进度优先于下一次排队。

边界：不补发整个应用停机期间尚未落库的 Cron 时刻；XXL-JOB 仍按原调度中心机制运行，不改为本队列。等待期间多次触发合并成一次后续运行，不是每个 Cron 时刻各执行一遍。暂时不可用的元数据库仍需恢复后才能派发。

**9. [P2] 前 256 条排队持续失败会挡住后面的任务**

位置：`SyncScheduleQueue.pending`、`SyncService.dispatchScheduledQueue`。

继续检查新队列时发现，每次派发都查询 `ORDER BY id LIMIT 256`。若这些请求因任务忙碌、连接或元数据故障持续留在 `queued`，后续请求即使可以正常启动也不会被扫描。已有执行名额不满时仍可发生。

修复：按运行 ID 维护分批扫描位置，并固定每轮扫描的最大 ID；到达上界或遇到空页后重新从头扫描。每条请求尝试后推进位置，名额不足而未尝试的请求留到下次；不断新增请求也不能阻止旧请求获得下一次机会。扫描位置仅在内存中影响公平性，等待请求、领取状态及业务续传断点仍在数据库；重启从头扫描，不丢失请求。每次最多读取 256 条，不使用 OFFSET，不新增表字段。
