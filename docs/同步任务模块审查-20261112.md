## 4. P0 问题

### 4.1 ClickHouse 同物理表判断可被别名绕过

位置：

- `src/main/java/com/el2ck/sync/SyncEngine.java` 约第 470-473 行。
- 后续全量清表路径约第 1071-1074、1096-1099、1117-1121 行。

当前判断只比较：

```java
source.getHost().equalsIgnoreCase(target.getHost())
    && qualifiedSourceTable.equals(qualifiedTargetTable)
```

它没有确认两个连接最终指向同一 ClickHouse 实例。例如以下配置可能指向同一张物理表，但字符串不同：

- `127.0.0.1` 与 `localhost`
- 内网 IP 与公网 IP
- 域名与 IP
- 同一实例的不同 HTTP/TCP 端口
- 负载均衡地址与实际节点地址

如果源表和目标表实际相同，全量任务可能执行 `TRUNCATE TABLE`，直接清空正在读取的源表。

建议修复：

1. 在执行任何 `TRUNCATE` 前建立“物理目标身份”校验，不能只比较配置字符串。
2. 分别通过源连接和目标连接读取实际服务身份和目标表身份，至少比较规范化后的服务器身份、数据库名和表 UUID。
3. 将物理身份写入执行前检查结果和日志；无法取得可信身份时拒绝全量清表。
4. 将这项检查放在所有可能清表的执行入口，包括普通分段任务、日期分表任务、重新传输和自动重试。
5. 后端增加强制保护；前端提示不能作为唯一防线。

这是本次审查中唯一建议在发布前无条件处理的问题。

## 5. P1 问题

### 5.1 增量水位回退后可能永久漏数

位置：

- `src/main/java/com/el2ck/sync/JdbcSegmentReader.java` 约第 129-177 行。
- `src/main/java/com/el2ck/sync/SyncEngine.java` 约第 1060-1093 行。

任务开始时保存源上界，之后只读取 `last < row <= upper`。如果源表被重建、历史数据被清理、水位列被回填，或源表最大水位小于已保存的 `last`，读取结果会为空，任务可能直接标记完成。之后新数据即使继续增长，也可能要超过旧断点才会被读取。

建议修复：

1. 每次运行记录源表标识或源表生成版本；表被重建时要求建立新基线。
2. 读取前比较当前源上界和已保存断点；当前上界小于断点或差异异常时明确失败。
3. 为迟到数据设置业务认可的 overlap 窗口，并用稳定键去重。
4. 对时间水位不能假设永远单调；若源系统允许更新或回填，应改用 CDC、版本列或可识别更新时间的方案。

### 5.2 迟到数据低于已确认水位不会重读

位置：

- `src/main/java/com/el2ck/sync/JdbcSegmentReader.java` 约第 165-168 行。
- `src/main/java/com/el2ck/sync/SyncEngine.java` 约第 1090-1093 行。

查询只接受大于 `last` 的复合游标。源端事务提交晚于水位值、离线补录、跨时区写入或业务回填时，新提交的数据可能低于已确认水位，后续批次不会包含它。

建议修复：

- 对不可变、严格单调的流水表，保留当前模式并在任务说明中明确约束。
- 对允许迟到写入的表，增加可配置回看窗口，例如每次从 `last - N 分钟` 开始扫描，再按稳定键或目标表去重。
- 对允许更新旧记录的表，增加版本列并采用“最新版本覆盖”写入协议。

### 5.3 增量更新目前是追加写入

位置：

- `src/main/java/com/el2ck/sync/SyncEngine.java` 约第 1117-1137 行。
- `src/main/java/com/el2ck/sync/SyncBatchWriter.java` 约第 133-152 行。

增量路径没有统一按业务主键执行更新或替换。写入协议主要是向 ClickHouse 追加数据；响应丢失重试依靠确定 token 去重，但不能保证“同一业务主键的新版本”只保留一条。

影响：

- 源记录修改后，目标表可能同时存在旧版本和新版本。
- 查询必须自行按主键、版本或时间取最新值。
- 普通 `count()` 和直接表查询可能高估有效数据。

建议先明确两类目标语义：

1. **追加型事件表**：源行不可变，按事件 ID 去重；当前追加模型适用。
2. **最新状态表**：必须有版本列或更新时间，使用 `ReplacingMergeTree(version)`，并规定查询使用 `FINAL` 或等价聚合；如果现有目标必须是普通 MergeTree，则应设计受控的删除加插入协议。

不能仅通过增加两个隐藏字段解决；应先确定表引擎、主键、版本列和查询口径。

### 5.4 日期分表编辑会用第一张预览表覆盖原参考表

位置：

- `web/src/views/SyncTasksView.vue` 约第 2225-2238 行。
- `src/main/java/com/el2ck/service/sync/SyncService.java` 约第 507-511 行。
- `src/main/java/com/el2ck/service/datasource/MysqlDateTables.java` 约第 63-70 行。

前端预览后直接取 `preview.tables[0]`，后端保存时也再次把 `sourceObject` 改成第一张匹配表。编辑任务时，即使原参考表仍存在，也可能被另一张表替换；如果不同日期表结构有漂移，字段映射和参考主键会随之变化。

建议修复：

1. 预览接口增加 `preferredTable` 或 `referenceTable`。
2. 编辑时若原参考表仍匹配规则且仍存在，优先保留原表。
3. 只有原表不存在或用户明确确认时才切换到新表。
4. 保存前比较各候选表的结构；参考表切换时给出差异摘要并要求确认。

### 5.5 新增/编辑初始化存在异步竞态

位置：

- `web/src/views/SyncTasksView.vue` 约第 1713-1832 行。

`openCreate()` 和 `openEdit()` 都会等待连接、源字段和目标表请求。若用户快速连续打开不同任务，较早请求返回后仍可能修改当前表单。`loadSourceCols()` 内部有请求序号保护，但整个新增/编辑会话没有统一代次。

建议修复：

1. 增加 `editorSessionSeq`，每次打开、关闭、切换任务时递增。
2. 所有异步结果写回表单前检查当前会话序号。
3. 同时使用 `AbortController` 取消不再需要的 HTTP 请求。
4. 抽屉关闭后禁止旧请求重新打开或覆盖表单。

## 6. P2 问题

### 6.1 目标表锁身份跨别名可能不一致

位置：

- `src/main/java/com/el2ck/sync/SyncEngine.java` 约第 497 行。
- `src/main/java/com/el2ck/sync/SyncCheckpointStore.java` 约第 151、267-269 行。

目标锁字符串由 `host + database.table` 组成。不同连接使用 IP、域名或端口别名访问同一目标表时，会生成不同命名锁。

建议：

- 使用与 P0 相同的物理目标身份生成命名锁。
- 锁必须覆盖跨节点、跨连接别名和不同端口。
- 当无法取得稳定身份时，宁可拒绝并发写入，也不要静默允许。

### 6.2 自动建表存在“先检查、后创建”竞态

位置：

- `src/main/java/com/el2ck/sync/SyncEngine.java` 约第 2394-2424、2500-2501 行。

流程先检查表不存在，再登记、授权并执行 `CREATE TABLE IF NOT EXISTS`。两个请求并发时，一个请求可能在另一个请求创建后继续执行，`IF NOT EXISTS` 又会返回成功，造成归属或后续授权判断不明确。

建议：

- 在元数据库中为物理目标身份建立唯一预留，并用短事务完成占位。
- 创建时校验目标表 UUID 是否属于本次请求。
- 创建后如果发现表已由其他任务产生，不能激活为当前任务目标。
- 失败清理只能删除本次确实创建的物理表。

### 6.3 未映射的目标额外列会静默取默认值

位置：

- `src/main/java/com/el2ck/util/SyncMappingTypes.java` 约第 70-87 行。
- 写入列清单由映射生成，未映射目标列不会进入 `INSERT` 列表。

当前校验只保证所有映射列存在，没有主动说明目标表中哪些额外列未映射。ClickHouse 会为这些列使用默认值或默认表达式，用户可能误以为所有目标列都已同步。

建议：

- 保存和执行前计算未映射目标列清单。
- 将无默认值、有默认值和系统允许列的规则分开。
- 在任务详情和运行日志中展示“由目标表默认值填充”的列。
- 对需要显式忽略的列建立白名单，避免结构变化后悄悄补空值。

### 6.4 响应丢失后的去重依赖有限窗口

位置：

- `src/main/java/com/el2ck/sync/SyncBatchWriter.java` 约第 17-19、133-152 行。

当前使用确定 token 和 ClickHouse 非复制表去重窗口。窗口足以覆盖正常重试，但长时间中断、目标设置被缩小或人工修改、ClickHouse 无法确认响应时，幂等边界仍受窗口限制。

建议：

- 保留现有 token 机制作为第一层保护。
- 在元数据库或专用 ClickHouse 控制表记录已确认 token 和行范围。
- 不确定响应恢复时，先按 token 查询确认状态，再决定重放。
- 定期审计目标重复率，特别是大表和长时间中断场景。

### 6.5 运行中任务仍显示冲突操作

位置：

- `web/src/views/SyncTasksView.vue` 约第 800-817 行。

`edit`、`toggle`、`remove` 没有根据运行状态禁用。虽然后端应继续做最终校验，但界面仍会诱导用户提交必然失败或存在竞态的操作。

建议：

- 运行、排队、接管中的任务禁用编辑、启停和删除。
- 只保留取消、运行历史和只读查看。
- 后端同时返回明确的状态冲突错误，不能只依赖前端禁用。

### 6.6 全量转增量的前端锁定范围不完整

位置：

- `web/src/views/SyncTasksView.vue` 约第 497、505 行。
- `src/main/java/com/el2ck/sync/SyncCheckpointFingerprint.java` 约第 15-23、30-46 行。

后端指纹包含数据源、日期规则、结构、映射、目标、分段键、批次大小、排序键、主键、分区表达式等。前端仅禁用增量键和分段键，其他字段仍可编辑，最终保存才收到“不能沿用旧水位”的错误。

建议：

- 已完成全量转增量时，锁定所有会进入旧全量指纹的字段。
- 允许修改的只有新表策略、定时设置等后端明确忽略的字段。
- 在表单顶部列出“本任务因继承全量基线而锁定”的原因。
- 提供“新建任务”入口处理确实需要更换配置的情况。

### 6.7 主列表操作列未固定

位置：

- `web/src/views/SyncTasksView.vue` 约第 132-136 行。

操作列没有 `fixed="right"`，横向滚动后操作入口会移出可视区域。日志抽屉的操作列已经固定，主列表与日志详情应保持一致。

### 6.8 主列表仍在前端筛选和分页

位置：

- `web/src/views/SyncTasksView.vue` 约第 882-893 行。

页面先加载任务列表，再在浏览器执行筛选和切片。任务较少时可用，但任务、运行状态和分组信息增多后，会增加首屏数据量和查询延迟。

建议：

- 将关键字、状态、启用状态、分页参数传给后端。
- 列表接口只返回当前页任务和必要的最近运行摘要。
- 将运行状态轮询拆成只刷新当前页运行摘要的接口。

### 6.9 键盘与辅助技术交互不完整

位置：

- `web/src/views/SyncTasksView.vue` 约第 44-53 行：流向文字只有点击处理。
- `web/src/views/SyncTasksView.vue` 约第 145-148 行：步骤条只有点击处理。
- `web/src/components/OptionalDateRangeInput.vue`：错误文本没有 `role="alert"`，日期输入没有 `aria-invalid` 和 `aria-describedby`。

建议：

- 可点击文字改为按钮或增加 `role`、`tabindex`、Enter/Space 处理。
- 向导步骤使用真正的可聚焦控件，并说明未完成前置步骤时不能跳转。
- 日期错误使用关联 ID，让读屏在错误出现时朗读。

### 7.1 映射删除按钮缺少可读名称

## 11. P0/P1 修复与展示优化

### 11.1 源/目标物理表保护

- 新增 `src/main/java/com/el2ck/sync/SyncTableIdentity.java`，读取真实 `serverUUID()`、表 UUID、引擎和库表名，不再用地址字符串证明源与目标不同。
- 表 UUID 相同，或服务器 UUID 和库表名相同，都会拒绝执行。读取身份失败不会降级放行。
- `SyncEngine.runInternal` 在选择分段/快照路径前统一检查；五处 `TRUNCATE` 调用统一经过 `truncateTarget` 再复核，覆盖空源、正常全量、重新传输和重试。
- 本轮源配置固定在线程上下文，复核不会重新读取执行期间被编辑过的数据源配置；执行结束清除上下文。
- View、Distributed、Merge 等间接源不能证明与目标隔离，因此当前明确拒绝；支持独立 MergeTree 系列源。目标仍遵守原普通 MergeTree 要求。
- 依据：[ClickHouse 表元数据](https://clickhouse.com/docs/operations/system-tables/tables)、[服务器身份函数](https://clickhouse.com/docs/sql-reference/functions/other-functions#serverUUID)。部署连接仍须指向稳定实例；不能把会在不同物理节点间切换的代理当作单实例连接。外部管理员在校验和 DDL 之间并发重命名/替换表不在应用锁的保护范围内。

### 11.2 水位回退检查与范围

- JDBC 分段增量首次执行与恢复时，比较当前源上界和已确认复合断点；空源或上界小于断点时明确失败，不清空目标，不自动回退水位。
- MySQL 日期分表的恢复路径重新检查当前源上界，不能因为上轮已经保存 `captured` 就略过检查。
- MySQL/PostgreSQL JDBC 快照、ClickHouse 增量快照在应用水位过滤条件前检查最大水位；未发现新增不再掩盖明显回退。
- 新轮次复用本次查询的上界，续传保留原冻结上界。已完整保存的快照仍按原快照恢复，不因源后来变化重采集。
- 顺带修复 `JdbcSegmentReader.baselineAt` 把 `DateTime` 当 `Date` 截至零点的问题：先判断时间戳，只有 Date/Date32 才取日期。
- **尚未覆盖：** 源重建后最大水位等于或高于旧断点、旧水位以内的数据更新或删除，无法仅通过最大值识别。本轮未引入源事务日志/CDC；不能声称所有重建或历史变化都已检测。

### 11.3 日期分表参考结构

- 预览请求携带当前 `sourceObject`，响应明确返回 `referenceTable`。参考表仍在匹配清单中时保留原表，不再使用 `tables[0]` 覆盖。

### 11.4 异步会话隔离

## 12. 后续完善（2026-11-13）

### 12.1 同步目标互斥与旧断点

- 所有现行断点执行入口及存量基线接管入口统一读取 `serverUUID()`，使用实例 UUID、库名、表名生成物理目标锁；建表前后锁名一致。地址或协议不同但物理实例和库表相同的任务不能并行写入，不同目标表仍可并行。
- 同时保留原地址锁与旧断点指纹，不因这次锁改动要求重新传输。两把锁共用同一元数据连接，保存断点前验证所有权，退出时全部释放；释放异常时终止连接。
- 在已有 `el_sync_checkpoints.state_json` 中新增可空的 `physicalTargetLock`。查找其他任务未完成写入时同时匹配旧锁、新锁或旧断点中的非零目标表 UUID，防止别名绕过失败轮次的保留。
- 写入准备前再次核对实例身份；已记录物理目标的未完成断点不能自动切换到另一个实例。
- **升级约束：** 停止所有旧版执行实例后再统一升级，不保证新旧版本混跑时旧执行器也持有物理锁。旧断点没有物理锁且目标表 UUID 为零时，不能反推历史连接别名是否指向同一表，需要核对未完成任务。外部管理员改名/换表、负载均衡连接在多实例间切换仍不受此锁保护。

### 12.2 同步自动建表

- 同步建表使用严格 `CREATE TABLE`，不再用 `IF NOT EXISTS` 把并发出现的同名表视为本次创建成功。
- 平台预留必须属于当前同步任务；同一用户的其他任务、工作流或手工资产不能被当作本任务的建表预留。
- 建表或授权失败时保留物理表及失败资产，保留原异常，不再调用按名称补偿删除。结果不确定时由管理员核对归属和授权后恢复。
- 本节只修改同步自动建表链路；不声称已为其他模块实现跨系统事务，也不能防止外部管理员在 CREATE 成功后立即替换表。

### 12.3 日期分表全量转增量

- 对具有完整逐表基线的全量任务，切换增量后锁定来源、规则区间、目标、映射、分段键、批大小和建表配置；结束日期自动清空，继续发现新日期表。新表策略与定时设置仍可调整。
- 先改配置再切换增量时，列出与原任务的差异并阻止继续保存，提供“恢复原同步配置”。后端指纹验证仍是最终防线。
- 历史 null、空字符串、空数组及默认批大小按编辑回显规则归一化，结构仅比较字段名称和类型，避免把默认值或注释元数据误判成结构变化。
- 恢复时重新读取当前结构；真实源结构变化不会被恢复按钮掩盖，仍须核对处理。
- 日期组件增加真实日历日期校验、错误读屏提示、输入错误关联和禁用态；删除映射按钮补充具体字段的无障碍名称。

- 原 UUID、元数据修改时间和物理实例锁检查继续保留；增加摘要比对，避免仅凭相同修改时间认定字段、默认值、排序、分区和表设置未变。
- 首次启用去重设置仍使用原有的持久化修改意图：只有表 UUID 与排除本次去重设置后的定义一致，才允许完成该受控修改并保存新摘要；不把任意 DDL 变化当成正常恢复。
- 继承普通增量、日期分表及 SFTP 下一轮断点时，一并继承定义摘要。全量转增量读取水位前检查摘要；显式接管的确认令牌绑定定义摘要，防止预览与确认期间只改结构却继续接管。
- 接管保存新状态时同时保留当前物理目标锁信息。旧断点缺少摘要时保留原 UUID/时间检查，在本次准备成功后记录当前定义；不能据此追溯证明升级前结构从未变化。

### 15.2 未确认子批次的版本

- 新增可空 `writerServerVersion`，复用目标元数据查询读取 `version()`；发出新子批次前与 SQL 摘要一起保存，不新增逐行或每批数据扫描。
- 已有未确认子批次且有原版本证据时，如果当前版本不同，停止重放并保留断点。普通已确认轮次不因版本字段本身而禁止后续升级，但仍需通过结构与其他写入条件检查。
- 旧未确认子批次没有版本证据时，继续保留原恢复契约并输出 `sync.legacy_chunk_version_unknown` 应用日志；不会把当前版本补写成该历史批次的已知原版本。成功响应后再记录本次已确认的版本。
- 版本变化或结构摘要不一致属于确定性校验失败，不作为网络瞬时错误反复自动重试。

### 15.3 不能由本轮证明的情况

- 普通 MergeTree 的 `non_replicated_deduplication_window` 是按块数保留，不按中断时长判断是否安全；本轮不增加任意“超过若干分钟必须重传”的限制。依据：[ClickHouse 重试去重说明](https://github.com/ClickHouse/clickhouse-docs/blob/main/docs/guides/developer/deduplicating-inserts-on-retries.md)。
- 摘要与版本一致不代表去重记录必然存在，也不能证明服务端崩溃过程中某次 INSERT 的每一行都已提交。平台外写入、清理去重日志、先改后恢复设置或底层存储异常仍不在该证据范围内。
- 尚未增加可独立核验业务写入结果的持久化收据/控制表；不能把本次加固说成窗口之外的 exactly-once 保证。单独在 MySQL 写“已提交 token”也无法原子证明 ClickHouse 提交结果。
- 摘要采用完整 CREATE 文本，升级导致定义的输出格式变化时也可能拒绝续传，需要核对；不会自动忽略无法解释的差异或清空目标。
