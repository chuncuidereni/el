# 标准源表删除后同步重建修复

日期：2026-10-20。

## 问题与原因

标准源表删除后，原同步任务仍保留，但旧表资产已退役。`SyncService.startRun` 和后台 `execute` 调用目标权限检查时固定传入 `allowNew=false`，忽略任务的 `autoCreateTable`，因此在进入建表逻辑前就报“目标表尚未分配给当前用户”。

SFTP 目录任务还有一处关联问题：旧表的文件同步记录仍在 `el_sync_files`。即使重建成功，未变化的文件也会被判为已同步，导致新表缺数据。

## 修复行为

- 同步启动及后台执行都按任务的 `autoCreateTable` 检查目标。启用自动建表时，已删除且名称空闲的目标可由原任务重新创建；不开启时仍拒绝自动重建。
- 沿用任务所有者身份、数据源归属校验、目标冲突检查和受控建表流程。普通用户不能借重建写入其他用户的表；已有未登记物理表也不能被自动认领。
- SFTP 目标不存在时，在创建物理表之前清理该任务的旧文件记录，随后重新导入当前远端文件。先清理再建表，避免建表后连接失败或进程中断，使下一次执行错误跳过文件；清理失败则不创建空表。
- 页面受控删除后的重建生成新资产，创建者仍为任务所有者；旧共享授权不继承，需要所有者重新共享。内置 admin 继续按业务 CK 账号的库级权限查看新表。
- 目标正常存在时继续按文件大小及修改时间去重，不强制重新导入。

涉及代码：`src/main/java/com/el2ck/service/sync/SyncService.java`、`src/main/java/com/el2ck/sync/SyncEngine.java`。没有新增数据库迁移或前端菜单。

## 验证

后端现有 47 项测试通过，Maven `package` 成功。

使用一次性 MariaDB 10.11、ClickHouse 25.3.14.14、JDK 17 应用实例和仅监听本机的 SFTP 服务，经真实 HTTP 接口验证：

1. 普通用户创建 SFTP 数据源和标准源表同步任务，首次导入 CSV 的 2 行，创建者正确，生成文件记录，可共享给另一用户。
2. admin 删除该表后，原任务普通同步成功重建，2 行全部重新导入；新资产 ID 与旧资产不同，创建者不变，旧共享用户不可见，admin 可见。
3. 再次普通同步写入 0 行，表仍为 2 行，确认正常文件去重保持有效。
4. 再删表并模拟 SFTP 断开：新表创建后连接失败，旧文件记录已清空；恢复 SFTP 后普通重试导入全部 2 行，复用该次新建资产。
5. 关闭自动建表后删表，执行被拒绝且物理表未重建；明确重新开启后同步成功。
6. 其他用户不能执行原任务或删除原用户私有表。目标名被其他用户新表占用时，原任务被拒绝，该表未被写入。
7. 同名目标为未登记物理表时，原任务被拒绝，原物理表及数据不变。

临时脚本、SFTP 数据、验证应用及专用数据库容器已清理；未新增最终保留的测试代码，原有测试文件保留。

## 应用

替换本次构建的 `target/el-to-ck-server.jar` 并重启后端应用。原任务需启用“自动创建表”，直接执行普通同步即可；无需删除重建任务，也无需重启 MySQL。

本次没有连接或修改 212 数据库，没有修改现有账号密码或重启现有部署。SFTP 重建会重新读取远端当前仍存在的文件，不能恢复远端已删除的文件；此次修复不处理 SFTP 服务端主动断开连接的原因。
