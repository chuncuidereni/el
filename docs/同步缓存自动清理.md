# 同步缓存自动清理

正常同步完成后仍立即清理本轮源快照和 SFTP 缓存。新增后台补清理任务处理异常退出、清理失败、任务删除和重新传输后残留的缓存，避免这些文件长期堆积。

默认启动 60 秒后首次扫描，此后每 10 分钟尝试一次。文件扫描、删除使用独立后台线程，不占用定时同步任务的调度线程；同一实例不会同时运行多个清理批次。

## 删除范围和保护规则

只检查 `/app/data/sync-resume/snapshots/sftp/task-任务ID/轮次UUID` 和 `/app/data/sync-resume/sftp/task-任务ID/轮次UUID`，只删除程序生成的 file-N.json、csv、xlsx、part、meta、meta.tmp、snapshot-manifest.sha256 及 round.lock。不递归删除任意目录，遇到符号链接或未知内容保留该轮目录。

| 数据库状态 | 操作 |
| --- | --- |
| 任务已删除，且没有 running 记录 | 清理该任务遗留轮次 |
| 当前断点已完成且没有未确认操作 | 清理当前轮次及更早的轮次 |
| 当前断点未完成 | 保留当前轮次，只清理已被替代的旧轮次 |
| 任务锁或文件锁被占用 | 跳过，等待下轮扫描 |
| 仍有 running 记录 | 跳过，由原有运行恢复机制先处理 |
| 数据库不可用、失锁、断点缺失或损坏 | 保留文件，不猜测、不按文件年龄删除 |

清理与执行、删除任务共用 MySQL 任务锁，取得锁后再读取最新数据库状态；实际删除还必须取得本机轮次文件锁。失败任务不会因为缓存放置时间较长而被自动清掉，仍可继续传输。清理过程中失锁或应用关闭会停止后续删除。

不会删除 MySQL 中的断点、增量水位、运行历史或文件去重记录，也不会删除上传源文件、DuckDB 文件、日志或 CK 目标表数据。任务删除后不必等待再次执行即可回收其缓存；最迟等下一轮扫描且锁可获取时处理。

2026-11-06 补充：未完成快照重新采集时，执行器在任务、断点及文件锁保护下，先清理同轮已失效的 JSON 分页和摘要清单，再连接源。必须确认没有完整快照、目标初始化、确认行数、待确认操作或待停止写入。原 SFTP 文件（包括保留编号 `file-2147483647.json`）以及下载断点不删。此项清理随重新执行发生；后台扫描仍保留未完成的当前轮次，不会擅自丢弃有效续传数据。

## 配置与核验

无需新增表或执行升级 SQL，更新程序后默认生效。可在应用配置 `app` 节点下添加以下设置；Docker 镜像使用 `docker/application.yml`，修改后需重新打包：

```yaml
app:
  sync-cache-cleanup:
    enabled: true
    initial-delay-ms: 60000
    interval-ms: 600000
```

清理发生时，日志输出 `event=sync.cache.cleanup`，包含删除的文件数、字节数、轮次数和失败数。遇到失败输出 task_id 和错误类型，不输出原始断点、密码或查询令牌。无内容可清理时不会每轮重复输出统计日志。

服务器查看：

```bash
docker logs --since 30m el-to-ck-app-1 2>&1 | grep 'event=sync.cache'
docker exec el-to-ck-app-1 du -h --max-depth=2 /app/data/sync-resume
```

大量源数据在未完成的快照同步过程中仍会占用磁盘，这是续传所需的工作数据；本功能回收的是可确认不再需要的文件，不是限制运行中的缓存大小。自动清理不能替代为大型任务预留磁盘空间。
