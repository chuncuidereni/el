# 默认断点续传与源快照

2026-10-29 更新：同步任务默认使用断点续传，页面不再提供开启开关或“全量重建”按钮。新任务、已有任务、手动运行、本地 Cron 和 XXL-JOB 使用同一入口。旧记录中的 resumable=false 不再关闭恢复能力；新保存任务写入 true。旧客户端提交 force=true 会被拒绝，不会暗中清表。

标准源到目标库的工作流使用单独的恢复引擎，见[工作流断点续传与定时恢复](工作流断点续传与定时恢复.md)。本次移除的是同步任务强制重建入口，不修改工作流的业务动作。

## 普通运行

- 未完成轮次自动继续，保留已确认进度。
- 上轮完成后，下次运行按原有全量覆盖、全量追加、增量或按文件增量策略开始下一轮。全量覆盖新一轮仍按配置清空目标；默认续传不把全量改成增量。
- SFTP 目录按路径、大小、修改时间跳过未变化文件；远端文件删除不自动删除历史目标数据。
- 完成记录已提交、仅响应丢失：自动重试返回该轮完成，不启动下一轮。
- 未完成断点与配置、源数据或目标身份不一致时停止，不自动放弃进度或清表。恢复原配置/数据后继续；无法恢复时使用新的空目标表建立任务。
- 旧增量目标已有数据但没有可信断点时，不猜测目标 MAX 水位、不清空历史数据，需要新的空目标表建立基线。

## 来源与恢复方式

| 来源 | 恢复方式 |
| --- | --- |
| MySQL/PostgreSQL 配置合法稳定键 | 按主键或“水位＋主键”分段，支持全量覆盖和增量 |
| 独立 ClickHouse 全量覆盖且配置稳定键 | 按源排序键首列分段，固定上界 |
| ClickHouse / CK_TABLE 普通 MergeTree 全量，未使用唯一稳定键 | 简单列排序、支持的非空标量列且无 TTL 时，按排序前缀窗口和完整行值分批读取、写入并落库断点；其他条件仍采集快照 |
| 上述数据库未配置稳定键或其他受支持策略 | 采集持久源快照，再按快照行号入库 |
| Hive | 专用 JDBC 游标采集持久快照，再按行号恢复入库 |
| MongoDB | 流式采集持久快照，支持全量及增量水位 |
| 本地 CSV/JSON/XLSX | 流式解析为持久快照，再按行号入库 |
| 库内 CK_TABLE | 用任务所有者连接；符合上述条件的全量表分批读取，其他策略采集快照，源与目标不能相同 |
| SFTP 单文件 CSV/JSON/XLSX | 按字节缓存下载，解析为快照，再按行号入库 |
| SFTP 目录 CSV/JSON/XLSX | 固定文件清单，下载按字节、入库按文件内行号恢复 |
| Kafka | 固定 Topic ID、分区及 read_committed 位点范围，逐分区恢复 |

每批 100–10000 行，默认 10000。数据库稳定键可选；配置后仍严格检查类型、映射和索引，不满足条件会拒绝，不静默降级。

## 快照恢复边界

快照按批保存到 app.dataDir/sync-resume/snapshots/。2026-11-06 起，数据页刷盘后把逐页 SHA-256 追加到该轮的 `snapshot-manifest.sha256` 并刷盘，再把页数、行数和游标保存到 MySQL；EOF 后保存整个清单的 SHA-256 和完整标记。运行断点不再反复写入完整哈希数组。旧完整快照首次恢复时自动迁移清单，不重新采集或清除已确认游标。源读取到 EOF 且完整快照状态确认后才开始修改目标。完整快照后，应用重启或目标写入故障可从未确认批次恢复，原文件删除或源表变化不影响该快照。

**快照采集尚未完成时，Hive、MongoDB、无键数据库游标和本地解析中断，会重新采集该轮快照。** 此时尚未修改目标，不拼接两次采集结果。这些路径实现的是持久快照后的批次续传，不是源端游标位置恢复。SFTP 已下载字节可复用；JSON/XLSX 解析仍可能重新开始。

重新采集前会在锁保护下删除同轮失效分页和清单，保留 SFTP 原文件及下载断点，避免上次采集更多页留下尾部垃圾。有完整快照、已确认行数或待确认写入时禁止如此重采。已有目标的引擎、依赖视图、身份、映射、同步 INSERT 及所需权限会在打开源之前预检，正式写入前再复检；预检不改变目标结构。

快照不是跨数据库事务，采集期间应保持源稳定。增量快照按持久上轮水位筛选，整轮确认后才将新水位用于下一轮。新数据须严格大于已完成水位；旧行修改、删除、迟到/回填和新增同水位记录不属于该机制的 CDC 范围。

每批使用前核验 SHA-256、行数和字段数；启动时只校验分页清单，不再先扫描全部缓存。未确认批次的缓存损坏或丢失时停止，不能用已变化的源替代已确认快照。完成状态未确认时保留缓存，确认后清理。部署须持久挂载应用数据目录，预留快照、下载及转换的磁盘空间。多实例恢复还需共享缓存，不能只共享 MySQL。

2026-11-05 更新：快照和 ClickHouse 行值分页不再新增或写入 `_el_sync_round`、`_el_sync_row`。轮次、行号、待确认批次摘要和子批次位置保存在 MySQL 的 `el_sync_checkpoints.state_json`，目标通过固定批次令牌去重。原有来源、入库时间等业务约定保持不变。详见[无额外目标字段的续传](无额外目标字段的续传.md)。

## 稳定键条件

- MySQL/PostgreSQL 使用单列整数主键。水位与主键不同，需要以前者、后者为前导列的升序联合索引，不接受部分索引。源水位列还必须声明为 `NOT NULL`；仅把目标映射设为不可空不能替代源约束。
- ClickHouse 源须为 MergeTree 系列，分段键是 ORDER BY 首个直接列。
- 键必须非空、唯一、不可变，映射保留相同整数类型且不可空，不能使用手机号转换列。增量水位支持非空整数、Decimal、日期、无时区时间。
- 本轮及恢复期间既有记录不可变，只追加本轮上界之后的数据。上界不是事务快照，有序追加不是 CDC。
- 专用读取连接跨批复用，时间保留小数秒；数据查询遵循任务超时设置，网络无响应保护独立保留。无统计时不额外全表 COUNT。

2026-11-06 更新：保存任务和执行任务都会检查 MySQL/PostgreSQL 复合水位的源非空约束。检查通过 `SELECT 水位列 FROM 源表 LIMIT 0` 读取 JDBC 元数据，不扫描整表。源定义允许 NULL 或驱动无法确认约束时明确拒绝，避免 SQL 比较过滤 NULL 后仍显示同步成功。即使当前数据恰好没有空值，可空定义也不能通过；应先补齐空值并由源库管理员设置 `NOT NULL`，或选择已有非空水位列。程序不会自动修改源表。

## SFTP 文件恢复

目录固定清单、大小、修改时间。下载约每 8 MiB 或 2 秒刷盘并保存前缀长度、SHA-256，断开后验证前缀并按字节继续；损坏前缀重新下载。

完整文件摘要在入库前持久化，重新下载须匹配原摘要。未下载完成的文件通过大小、修改时间核对版本，无法识别保持同大小、同修改时间的内容替换；上游应上传临时文件后原子重命名发布，并保持发布内容不变。

目录目标保留原有的 `path String` 来源路径，不再新增 `_el_file_row`。文件行号和子批次位置保存在 MySQL；变化文件仍按既有路径替换策略处理。文件入库完成但文件完成记录保存失败时，只补记录，不重写文件。

CSV 按逻辑记录计行，支持引号内换行。恢复解析会顺序跳过已确认前缀一次，不是文件内随机定位。JSON/XLSX 使用现有解析器。列名或顺序不匹配则排除、保留该文件旧数据并继续其他文件。文件替换期间可能暂时只包含部分记录，不提供整文件原子发布。

## Kafka 位点恢复

只支持全量快照，不是持续流式消费。新增分区和超出上界消息留给下一轮；只确认已处理范围，不提交消费组位点，不确认预取未处理的消息。分区、消息位点和轮次只存入 MySQL，不再向目标新增 `_el_kafka_partition`、`_el_kafka_offset` 或 `_el_sync_round`。

已中止事务不写入；tombstone 跳过行但推进位点，不按 key 删除历史行。仅支持 cleanup.policy=delete 和有效非零 Topic ID。账号需消息读取、Topic 描述及配置读取权限。消息过期、Topic 重建、截断时拒绝跳过缺失范围。格式、鉴权及明文手机号错误不重试。

## 目标与自动重试

目标须是任务独占的普通 MergeTree，关闭 async_insert。依赖物化视图、复制表、分布式表、聚合表仍拒绝本恢复协议；删除重放无法回滚下游视图副作用。默认接入不会自动删除物化视图或改引擎。

写前记录未确认范围、固定转换时刻和摘要，每条 INSERT 成功后保存子批次位置，整批确认后推进源游标。恢复先停止本轮遗留写入，再按相同令牌和相同 SQL 重试，正常新协议不删除目标行。首次由受控管理操作启用表级 `non_replicated_deduplication_window=20000`；不新增目标字段，也不授予业务账号通用修改表设置权限。旧协议 pending 升级时仍需按旧字段清理一次，SFTP 文件替换仍需要 ALTER DELETE；清表策略仍需要 TRUNCATE。

同一轮可识别网络故障最多自动恢复 5 次，间隔 2/4/8/16/30 秒；ClickHouse 分段只读查询另有最多三次重试。MongoDB 连接和选择服务超时进入同一预算，鉴权失败除外。SQL、结构、数据校验、磁盘错误及主动取消不盲目重试。

2026-11-06 补充：源结构读取、CK 建连及目标库/表预检保留底层异常原因，使可识别的瞬时连接错误能进入已有自动恢复。重试次数和错误分类规则不变；配置、权限或数据问题仍需处理后再执行。

任务超时默认 0（不限总时长）。前端新建表单、后端任务对象和接口未传超时时的默认值一致。已有任务保留保存的超时值；以前的 30 分钟任务需编辑为 0。非零超时仍生效，重试不延长时限。

2026-11-06 更新：MySQL/PostgreSQL 分段读取、JDBC/Hive 快照的语句超时，以及 ClickHouse 行值分页的 `max_execution_time` 都跟随任务设置：0 不再转换成 1800 秒或 60 秒，非零分钟数也不再被截断为 30 分钟。连接探测、元数据查询、估算和网络无响应保护仍有独立限制；例如不限时 JDBC/Hive 任务仍保留 1805 秒的网络读空闲保护。持续接收数据的长查询不会仅因总耗时超过 30 分钟被本次修改涉及的语句计时器取消，但长时间没有任何网络返回仍可能失败。任务取消机制继续生效，ClickHouse 服务端账号及资源策略仍可能另外限制执行。

重新传输遇到旧轮次待确认写入时，先把旧令牌存入 `el_sync_checkpoints.state_json.pendingStopTokens`，再执行终止。确认停止并成功保存清理结果后，才能采集新一轮数据、重建或写入目标。停止失败、应用退出或确认响应丢失后，下次执行仍按落库状态恢复；连续重新传输也会继承待停止令牌。在此期间禁止更换任务和连接配置，也禁止其他任务写入该目标。无在途写入的正常新轮次不额外执行终止操作。

## 2026-11-05：无唯一键 ClickHouse 大表全量优化

任务 19 的历史失败原因是采集整表快照达到 30 分钟总时限，目标尚未开始写入；未完成快照再次运行会重采。符合条件的普通 MergeTree 表现在使用物理排序前缀划定小窗口，窗口内按完整源行排序。相同行值以已消费次数区分，保留重复手机号，不依赖转换后的目标列。字符串游标按字节编码，DateTime 游标按 epoch 保存。

每批先读取，再持久化待确认游标和摘要，目标写入确认后推进断点。写入结果不确定时，使用固定子批次令牌恢复。断点保存在 `el_sync_checkpoints.state_json`，不需要新增 MySQL 表或字段；目标不再新增 `_el_sync_round`、`_el_sync_row`。

当前自动分页支持普通 MergeTree、直接列组成的非空排序键，以及非空整数、String、Date、Date32、DateTime（含时区）列。不自动应用于 Nullable、DateTime64、浮点数、复杂类型、TTL、ALIAS 计算列、聚合表、复制表或复杂排序表达式。不满足条件仍使用原快照路径；已开启分页后源身份或结构改变则停止恢复。大量行具有相同排序前缀时，窗口内排序仍可能较慢；2026-11-06 起，数据查询超时跟随任务设置，不再固定为 60 秒。

行值分页不是事务快照：本轮及恢复期间不要改写、删除历史行，也不要向已读位置回填数据；普通后台 MergeTree 合并不改变行值顺序。固定上界之后的追加不进入本轮。小于上界的并发插入可能被本轮读取或错过，不能将该方式作为 CDC；严格一致的全量基线应读取停止变化的源表，持续新增由合适的增量键接续。

旧任务只有在配置指纹一致、快照尚未完成、未初始化目标、确认行数为 0、没有待确认写入和目标身份时才自动切换。已完成快照或已写入的旧任务继续原路径。切换后的旧缓存在任务空闲时由现有清理器回收；新的分页过程不再生成整表磁盘快照。不要把已经生成新模式断点的任务交给旧版程序继续运行。

本次使用实际源表做只读核验：两批各 10,000 行与同范围 20,000 行有序结果一致，补充排序键条件后上界重复计数仅扫描 1,427 行。未执行生产目标写入、整表完成验证或故障注入，不新增测试类。部署与操作步骤见 [ClickHouse 大表全量部署说明](ClickHouse大表全量部署说明.md)。

## 应用内 Cron 排队

2026-11-06 起，应用内定时触发先保存为 MySQL `el_sync_runs` 的 `queued` 记录。并发上限仍是每实例 3 个任务，满载或同任务正在执行时等待，不丢弃本次请求。派发器约每 5 秒扫描一次，取得名额及任务锁后沿用该记录开始执行，并默认续传。

同任务最多保留一个等待请求，等待期间多次到点合并成一次后续执行。排队不占执行名额；记录保存最晚已覆盖触发时刻，完成后仍保留去重身份。重启后恢复已经落库的等待请求，不补发整个应用停机期间尚未落库的 Cron 时刻。XXL-JOB 保留原调度中心行为。

队列每次最多扫描 256 条，并按运行 ID 分批推进。前面的任务持续忙碌或暂时失败时，后面的请求仍能获得尝试机会。每轮固定扫描上界，扫描结束后回到前部重试；运行名额满载时暂停扫描，尚未尝试的请求不会被跳过。

页面显示“等待执行”；当前轮运行时显示“下次已排队”，进度仍展示当前轮。可“取消排队”后手动执行或重新传输；该操作不终止已经启动的运行，也不停止后续 Cron。编辑任务会原子取消旧排队；停用或删除也处理等待请求。排队被取消时保留结束记录与原因。

“接管已有全量数据”根据落库断点禁用并提示具体原因。有水位、写入进度、待确认写入或排队的任务应继续原任务或先取消排队；预览/确认仍会校验配置指纹与目标状态。
