# 标准源到目标库：工作流断点续传与定时恢复

适用于页面中的多源仲裁工作流：标准源表 → 聚合表 `_agg` → 服务表/视图 `_svc`。生成、重建、单独刷新服务表共用持久断点。同步映射任务使用另一套断点，见[大表分段同步与断点续传](大表分段同步与断点续传.md)。

## 执行与恢复

1. 执行前取得 MySQL 工作流命名锁，再创建运行记录。手动、后台和定时共用该锁；正在执行时跳过重复触发。长任务不会因为运行超过六小时或其他实例启动而被误判为失效。
2. 为本轮创建固定的数据快照。每张源表在复制分区成功后保存快照 UUID；未确认的快照重新复制，已经确认的快照继续使用。多张源表的快照并非一个跨表事务。
3. 按转换后的号码有序分段。同一号码的明细不会被拆开。边界先取有限行数，再对这一小段去重，避免每段都对全部剩余号码做全量去重。
4. 聚合回填先写本段临时表，再用 `REPLACE PARTITION` 替换聚合暂存表中本段的分区。替换完成才保存断点；应答丢失时重复替换同一分区，避免 `sum` 重复累加。
5. 含 `sum` 的工作流按号码区间摊平到普通 MergeTree 暂存表。写入前保存待确认区间；恢复时先终止本轮遗留查询，再同步删除该未确认区间、重新写入。已经确认的区间保留。
6. 所有分段完成后发布。换表前保存新旧表 UUID；重试先核对正式表是否已经是本轮的新表，避免再次 `EXCHANGE` 把旧数据换回来。聚合表与服务表分别发布，并非两表联合原子事务。
7. 恢复物化视图并保存完成状态，随后清理本轮临时对象。清理失败不会把已经完成的任务改成失败，下次执行先补清理。

没有 `sum` 的服务层继续使用实时视图，不额外生成物理服务表。单独摊平会先固定聚合层快照；本轮执行期间聚合层如果又发生变化，会在后续自动检查时再次刷新，避免只比较表写入时间而漏掉增量。

## 定时触发与应用重启

- 工作流自动检查先查未完成断点，再判断服务表是否落后。未完成的是回填，就恢复回填；未完成的是摊平，就恢复摊平。不会因为旧服务表看起来“不落后”而漏掉失败任务。
- 同一轮遇到可识别的连接故障，默认自动重试五次，间隔约 2、4、8、16、30 秒。成功才通知；最终失败保留原因和断点。鉴权、SQL、配置和数据校验错误不在同一轮盲目重试。
- 重试次数用尽、应用重启、元数据库连接失效后，后续定时检查重新取得锁并从已持久化断点恢复。启用自动检查的工作流会被继续处理；停用工作流或关闭自动检查后，需要手动触发。
- 一轮完成后，下一次正常触发才建立新快照、新轮次。“重建”遇到未完成断点也先续传；确实要放弃断点，使用已有的“清理已生成的数据”操作后重新执行。
- 修改未完成任务的源、映射、聚合规则或目标会被拦截，防止把两种配置的数据混在同一结果里。可以在任务不运行时停用它。
- 同步映射的本地 Cron 和 XXL-JOB 都调用 `startScheduledRun`，以任务持久化所有者身份进入普通执行入口；同步任务现默认使用断点，定时触发同样恢复未完成轮次。不同来源采用稳定键、位点、文件行号或持久源快照，具体边界见[默认断点续传与源快照](大表分段同步与断点续传.md)。

## 配置和页面

```yaml
app:
  arb-flatten-interval-ms: 60000
  arb-resume:
    batch-keys: 100000
    statement-timeout-seconds: 1800
    max-retries: 5
```

`batch-keys` 为每段边界查询的候选号码行数，限制为 1,000～1,000,000；重复号码可能使实际号码数更少，同一号码的所有明细仍完整聚合。`statement-timeout-seconds` 是单条 SQL/网络等待的上限，最小 60 秒，默认 30 分钟；整轮任务没有额外的固定 30 分钟限制。以上参数可通过 `APP_ARB_RESUME_BATCH_KEYS`、`APP_ARB_RESUME_STATEMENT_TIMEOUT_SECONDS`、`APP_ARB_RESUME_MAX_RETRIES` 覆盖。

页面调用新增的 `POST /api/arb-workflows/{id}/start?action=setup|rebuild|flatten` 获取运行号，通过 `GET /api/arb-workflows/{id}/runs/{runId}` 轮询。关闭页面只停止观察，不取消后台执行。原同步执行接口仍保留兼容。后台工作流并发上限为每实例两个。

执行历史每三秒静默刷新，显示本轮阶段、已确认批次、行数、重试次数及总耗时。回填行数是各源已聚合号码数的累计；进入摊平阶段重新统计，最终成功行数是服务层号码数。未知总量不显示虚构百分比或 ETA。

## 部署和边界

- 工作流使用 `el_arb_checkpoints` 元数据表，不重建业务表。应用已停用自动迁移，缺少该表时先执行 [MySQL 手工补齐 SQL](mysql/20261029_resume_and_progress.sql)，再部署新版后端和前端；不要单独删除断点表或 `__elarb_` 临时表。
- 当前固定快照路径支持普通 `MergeTree`、`ReplicatedMergeTree` 标准源表；目标库需为 `Atomic`。源表不能带 TTL，避免快照在续传期间自行删除数据。其他引擎明确报错，不假装支持安全续传。
- 快照和暂存结果占用存储；未完成轮次保留这些对象，成功或显式清理产物后再删除。分段通过 CK 内部的 `INSERT SELECT` 执行，不把数千万行拉到 Java 堆内存。
- 原有的全量回填会暂时停止源物化视图。固定快照之后、物化视图恢复之前新写入源表的记录，仍需要下一轮全量重建补入。因此全量回填应安排在标准源同步结束后，避免同时写源表；本实现不是源写入与全量发布之间的事务切换。
- 号码处理后与源排序键不匹配时，选取边界仍可能扫描较多源数据；某个号码拥有大量明细时，一个分段也可能很慢。续传保护已确认进度，不承诺任何规模都不会超时。

实现使用的 ClickHouse 语义参考官方文档：[分区复制与替换](https://clickhouse.com/docs/reference/statements/alter/partition)、[EXCHANGE](https://clickhouse.com/docs/reference/statements/exchange)。

补充验证已覆盖已有目标表的 EXCHANGE 后中断恢复、无 sum 的实时服务视图及其增量更新、空源表。临时验证库已清理。
