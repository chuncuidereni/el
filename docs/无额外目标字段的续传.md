# 无额外目标字段的续传

2026-11-05 起，同步任务不再自动添加 `_el_sync_round`、`_el_sync_row`、`_el_file_row`、`_el_kafka_partition`、`_el_kafka_offset`。字段映射不会因为续传被扩展。既有来源、入库时间以及 SFTP 目录的 path 字段仍遵循原业务约定。

## 保存位置与写入顺序

继续使用 MySQL `el_sync_checkpoints.state_json`，不需要手工修改表结构：

- `token/last/pending/pendingHash`：本轮标识、已确认游标、待确认游标、源批次摘要。
- `pendingStopTokens`：重新传输时尚未确认停止的旧轮次令牌列表；2026-11-06 新增于现有 JSON，旧记录缺失此字段按空列表读取。
- `writerMode`：`mysql-dedup-v1`；区分旧的按辅助列删除重放协议。
- `batchTime`：本批固定转换时刻，重试的入库时间和 now()/today() 默认值保持相同。
- `chunkOffset/chunkHash`：已确认的子批次位置与当前 INSERT 摘要。
- `targetLock`：目标表保留标识；其他平台任务不能越过未完成任务写入同一表。
- `dedupSetupSchema/dedupSetupUuid`：启用去重设置期间的恢复信息，完成后清空。
- `snapshotPageCount/snapshotManifestHash`：2026-11-06 起记录快照页数及独立清单的 SHA-256；逐页摘要保存在本轮数据卷的 `snapshot-manifest.sha256`。旧 `snapshotHashes` 数组只用于完整快照升级，不再随每次进度更新重复写入 MySQL。

每条 SQL 最多 10000 行、约 1 MiB 字符（单行超长时不截断）。发送前保存摘要，成功后先保存子批次位置，再发送下一条。响应丢失则重建相同 SQL、使用相同 `insert_deduplication_token` 重试；整批确认后才推进源游标。MySQL 不保存整批业务数据或 SQL 正文，避免制造与源数据等量的元数据库及 binlog。

重新传输会先持久化待停止的旧令牌，再调用旧写入终止逻辑，最后逐个清除已确认停止的令牌并保存。在全部停止义务完成前，不采集新轮次、不重建或写入目标、不允许接管基线或标记完成。停止失败、进程退出、确认落库响应丢失或连续重新传输都不能丢弃这些令牌；其他任务也不能越过待停止状态写入同一目标。待停止期间必须保留原任务及连接配置，避免同主机切换端口后把停止命令发往错误实例。

## 目标设置与限制

首次接入启用普通 MergeTree 的 `non_replicated_deduplication_window=20000`；已有更大窗口不缩小。此操作只修改表设置，不改变列、排序键或字段映射。受控管理操作先验证业务账号有目标 INSERT 和 ALTER DELETE 权限，使用已有管理身份修改固定设置；没有权限就停止，不假装已具备去重能力。

只支持独立、没有依赖物化视图的普通 MergeTree，并使用同步 INSERT。目标必须由本任务独占写入：失败等待及恢复期间也不要从平台外写入、删改、TRUNCATE、启停去重窗口或清理去重日志。平台内由 MySQL 锁和未完成任务保留检查保护；平台外操作无法被 MySQL 锁阻止。

ClickHouse 去重日志有容量限制，不能把任意跨库写入宣传成分布式事务；本实现每次只留一个未确认子批次，并阻止其他平台任务推进该目标。管理员绕过平台写入或删除去重日志后，不能再保证安全重试。参见 [ClickHouse 重试去重官方说明](https://clickhouse.com/docs/guides/developer/deduplicating-inserts-on-retries)。

## 升级旧任务

重新打包部署后生效。无需更改任务映射或 MySQL DDL；不可回退旧程序运行新协议断点。

旧断点没有 pending 时直接进入新协议；存在旧 pending 时，先终止旧写入、验证源摘要，并使用原辅助列清理旧未确认区间一次，再切换新协议。原辅助列已被手工删除而仍存在旧 pending 时会停止，不能跳过清理直接重试。

升级不会自动 DROP 已存在的辅助列，也不会删除业务数据。旧列在新协议中不再出现在 INSERT 字段列表，但 ClickHouse 会对现存列填默认值。清理旧列应在相关旧断点处理完成、任务空闲后单独安排；活动断点仍会校验目标结构，运行途中改表会阻止恢复。

手动执行、自动重试、定时、全量、增量、文件及 Kafka 同步共用该写入协议。SFTP 已有“变化文件按 path 替换”业务行为保持不变。

## 2026-11-15：恢复防护补充

在既有 `state_json` 中增加 `targetDefinitionHash` 和 `writerServerVersion`，不需要 DDL，也不增加目标字段。准备写入时比对完整目标定义，继承普通增量、日期分表、SFTP 或全量基线时同时保留该证据。显式接管的预览确认也绑定目标定义摘要。

新子批次发出前保存观察到的 ClickHouse 版本。有未确认子批次且原版本已知时，跨版本恢复会停止，不直接重放。旧未确认子批次未记录版本的情况仍按原契约处理并输出应用日志，不能事后证明其原版本。已确认批次不因版本字段本身被禁止继续执行，但目标结构仍须通过核对。

普通 MergeTree 的去重窗口按块数保留，本次没有增加按中断时长强制重传的限制。结构和版本检查也不能证明去重日志未被删除或挤出；窗口之外的可靠确认仍未实现。不可把这些字段作为目标写入收据，更不能据此保证任意故障下都无重复、无遗漏。

本轮通过 Java 8 编译与内存脚本行为检查，覆盖摘要变化、版本变化、继承和 JSON 序列化；未新增测试类，未连接数据库或服务器，未重新打包部署。详见 [审查文档第 15 节](同步任务模块审查-20261112.md#15-恢复时的结构与版本证据2026-11-15)。
