# 登录框架与权限改造方案

> 状态：设计稿，未实施。本文只描述方案与迁移步骤，不含代码改动。
> 选型：**Sa-Token**（第三方方案里最轻，单依赖、无 Redis）。
> 适用范围：平台登录/会话层替换 + 功能权限（菜单/按钮）+ 数据权限（库表/资源）扩展。
> 部署前提：**单实例**（当前 212 单容器），**不引入 Redis**。

## 1. 目标与结论

### 1.1 目标

1. 用第三方登录框架替换现有 Spring Security 会话层，降低自维护成本；
2. 支持功能权限（角色 → 权限点 → 菜单/按钮/接口）；
3. 保留并扩展现有数据权限（资源归属、表级授权、共享）；
4. 单实例部署下不新增中间件，改造可回滚。

### 1.2 结论：不需要 Redis

| 需求 | 是否需要 Redis | 原因 |
|---|---|---|
| 单实例登录会话 | 否 | Sa-Token/Shiro 默认内存存储即可 |
| 功能权限判断 | 否 | 权限数据存 MySQL，进程内缓存足够 |
| 数据权限判断 | 否 | 现有 `ResourceAccessService` 查 MySQL |
| 登录限流 | 否 | 现有内存 Map 在单实例下有效 |
| 多实例/滚动发布 | 是（届时再引入） | 会话与限流需要跨 JVM 共享 |
| 在线会话/互踢/单点登录 | 是（届时再引入） | 需要共享会话索引 |

## 2. 现状盘点

### 2.1 认证与会话

| 组件 | 位置 | 现状 |
|---|---|---|
| Spring Security | `pom.xml`、`config/SecurityConfiguration.java` | 仅用于 session 上下文、CSRF、401/403 出口；未使用 `@PreAuthorize`/`GrantedAuthority` |
| 登录 | `controller/auth/AuthController.java` | `POST /api/login` 校验账号密码，写 `SecurityContext` + `HttpSession`，返回身份 |
| 会话校验 | `config/SessionAuthFilter.java` | 每请求校验：用户存在、`enabled`、`auth_version`、12 小时有效期、强制改密 |
| 身份上下文 | `config/AuthContext.java` | ThreadLocal，业务代码共 **99 处**调用 |
| CSRF | `SecurityConfiguration` | `HttpSessionCsrfTokenRepository`，前端写请求带 `X-CSRF-TOKEN` |
| 登录限流 | `AuthController.throttle` | 单 JVM 内存 `Map`，按 IP 60 秒窗口 |
| 旧 Basic 认证 | `config/BasicAuthFilter.java` | 已无注册点，仅 `writeJson` 静态方法被复用，属死代码 |

会话配置（`application.yml` / `docker/application.yml`）：

```yaml
server.servlet.session:
  timeout: 30m
  cookie: { http-only: true, same-site: lax, secure: ${SESSION_COOKIE_SECURE:false} }
```

### 2.2 当前授权

| 层 | 位置 | 现状 |
|---|---|---|
| 角色 | `el_app_users.role` | 只有 `admin` / `user` 两种 |
| 功能限制 | `config/RoleAuthFilter.java` | 硬编码“方法 + 路径”规则，仅限制 `user` |
| 前端可见性 | `web/src/stores/auth.ts` 的 `USER_ALLOWED_PATHS` | 路由白名单，`user` 仅能进首页/数据源/工作台等 |
| 数据权限 | `service/auth/ResourceAccessService.java` | 资源归属、表级授权、可见库表、共享 |
| 账号安全 | `service/auth/AccountSecurityService.java` | 启用、强制改密、`auth_version` |

`RoleAuthFilter` 当前拦截的 `user` 操作（可作为权限点初稿）：

- `/api/app-users/**`、`/api/tools/**`、`/api/system/**` 全拦；
- `PUT /api/settings`；
- `POST /api/connections`、`POST /api/connections/test`；
- `PUT|DELETE /api/connections/{id}`；
- `/api/connections/{id}/test|test-config|default|settings|server-stats|users/**`。

### 2.3 关键约束

1. `AuthContext` 被业务代码大量使用，**改造时保持其接口不变**，只替换“谁往里写”。
2. `auth_version` 机制保证改密/禁用/撤权后会话立即失效，必须保留。
3. 现有前端依赖 Cookie 会话 + CSRF token，换 token 方案要同步改前端。

## 3. 选型（已定：Sa-Token）

要求是“最轻”，结论：**用 Sa-Token**。它是第三方方案里依赖最少、接入最简单的：

| 方案 | 新增依赖 | 单机 Redis | 改造量 | 结论 |
|---|---|---|---|---|
| **Sa-Token** | 1 个 starter（约几百 KB） | 不需要 | 中 | **选定** |
| Shiro | 1 个 starter + 配置类 | 不需要 | 中高 | 偏重，不选 |
| JWT | 需自行实现刷新/吊销/互踢 | 不需要 | 中高 | 不选 |
| 保持 Spring Security | 0（已在依赖里） | 不需要 | 低 | 绝对最轻，但用户要求换第三方框架，仅作备选 |

选择 Sa-Token 的理由：

1. 单机零外部组件，`SaTokenDao` 默认内存实现；
2. 登录、登出、踢人、多端登录、权限注解都是现成的；
3. `StpInterface` 可以直接对接 MySQL 权限表；
4. 以后真要多实例，只加 `sa-token-redis-jackson` 一个依赖，业务代码不用改。

> 如果哪天认为“连第三方都不想引”，保持现有 Spring Security 并补 `GrantedAuthority` 才是绝对最轻；本文按“换第三方”的前提编写。

## 3.1 最小接入清单

只做必要的事，避免过度设计：

1. `pom.xml`：移除 `spring-boot-starter-security`，加入 `sa-token-spring-boot-starter`；
2. `application.yml`：只配 `token-name`、`timeout`、`is-concurrent`、`is-share`；
3. `AuthController`：登录改 `StpUtil.login(userId)`，登出改 `StpUtil.logout()`；
4. 新增一个拦截器：迁移 `SessionAuthFilter` 的四条校验（启用、`auth_version`、12 小时、强制改密），并在其中 `AuthContext.set(...)`；
5. `StpInterface`：查权限表返回权限点（带 60 秒缓存）；
6. 删除 `SecurityConfiguration`、`SessionAuthFilter`、`SessionIdentity`、`BasicAuthFilter`；
7. 前端：`http.ts` 加 `Authorization` 头，`auth.ts` 改用权限点。

`AuthContext` 的 99 处调用、`ResourceAccessService` 的数据权限、`AccountSecurityService` 的账号安全逻辑**全部不动**。

## 4. 目标架构

```
请求 → Sa-Token 拦截器
        ├─ 未登录 → 401
        ├─ 账号禁用/auth_version 变化/超时 → 踢下线 + 401
        ├─ 强制改密 → 仅放行 /api/me、/api/me/password、/api/logout
        ├─ 功能权限（@SaCheckPermission 或统一拦截）→ 无权限 403
        └─ AuthContext.set(userId, username, role)   ← 业务代码零改动
              ↓
        业务 Service
              ├─ 数据权限：ResourceAccessService（归属/授权/可见性）
              └─ 审计：el_access_audit
```

### 4.1 会话与 token

- 登录成功 `StpUtil.login(userId)`，token 通过 **Header**（`Authorization: Bearer <token>`）下发；
- 会话数据存 Sa-Token 默认内存（`SaTokenDaoDefaultImpl`）；
- 超时时间保持 30 分钟，同时保留现有 12 小时绝对有效期（在拦截器里判断 `loginTime`）；
- 登出 `StpUtil.logout()`，并清理 `AuthContext`。

> token 放 Header 后，CSRF 风险基本消失（浏览器不会自动携带）。若坚持 Cookie 存储，必须保留 `SameSite=Lax` 并自建 CSRF 校验。

### 4.2 与现有机制对应关系

| 现有 | 改造后 |
|---|---|
| `HttpSession` + `SessionIdentity` | Sa-Token token + `SaSession` |
| `SessionAuthFilter` | Sa-Token 拦截器 + `StpInterface` |
| `SecurityContextHolder` | `StpUtil.getLoginIdAsLong()` |
| `AuthContext` | 保留，由拦截器填充 |
| `RoleAuthFilter` | 权限点校验（`@SaCheckPermission` / 拦截器） |
| `HttpSessionCsrfTokenRepository` | Header token 方案下移除 |
| `AuthController.throttle` | 保留内存实现（单实例） |

## 5. 数据模型（MySQL）

新增 4 张表，按项目约定写成 `docs/mysql/` 下的手工 SQL（可重复执行），不进入启动自动迁移。

```sql
-- 角色
CREATE TABLE IF NOT EXISTS el_roles (
  id BIGINT NOT NULL AUTO_INCREMENT,
  code VARCHAR(64) NOT NULL,
  name VARCHAR(128) NOT NULL,
  description VARCHAR(255) NOT NULL DEFAULT '',
  builtin TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY el_role_code (code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin;

-- 权限点
CREATE TABLE IF NOT EXISTS el_permissions (
  id BIGINT NOT NULL AUTO_INCREMENT,
  code VARCHAR(128) NOT NULL,
  name VARCHAR(128) NOT NULL,
  group_name VARCHAR(64) NOT NULL DEFAULT '',
  description VARCHAR(255) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  UNIQUE KEY el_perm_code (code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin;

-- 角色-权限
CREATE TABLE IF NOT EXISTS el_role_permissions (
  role_id BIGINT NOT NULL,
  permission_id BIGINT NOT NULL,
  PRIMARY KEY (role_id, permission_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin;

-- 用户-角色
CREATE TABLE IF NOT EXISTS el_user_roles (
  user_id BIGINT NOT NULL,
  role_id BIGINT NOT NULL,
  PRIMARY KEY (user_id, role_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin;
```

兼容策略：

- 现有 `el_app_users.role` 保留，作为“超级管理员/普通用户”的粗粒度兼容字段；
- 初始化脚本把 `admin` 映射到内置角色 `super_admin`（拥有全部权限点），`user` 映射到 `member`；
- 后续新增角色只写新表，不再扩展 `role` 枚举。

### 5.1 权限点命名

格式 `模块:动作`，与接口一一对应：

```
sync:view        sync:run        sync:create     sync:edit      sync:delete
conn:view        conn:create     conn:edit       conn:delete    conn:test
ds:view          ds:create       ds:edit         ds:delete
table:view       table:create    table:alter     table:drop     table:truncate
query:view       query:run       query:export
workflow:view    workflow:run    workflow:edit   workflow:delete
settings:view    settings:edit
user:view        user:create     user:edit       user:delete
system:view      tool:use
```

数据权限不设权限点，继续由 `ResourceAccessService` 按资源判断。

## 6. 后端改造

### 6.1 依赖与配置

```xml
<!-- 替换 spring-boot-starter-security -->
<dependency>
  <groupId>cn.dev33</groupId>
  <artifactId>sa-token-spring-boot-starter</artifactId>
  <version>{版本}</version>
</dependency>
```

```yaml
sa-token:
  token-name: Authorization      # 或自定义 header
  timeout: 1800                  # 30 分钟
  active-timeout: -1
  is-concurrent: true            # 是否允许同账号多端登录（按需求定）
  is-share: false
  token-style: uuid
  is-log: false
```

> 若保留 Cookie 模式，改 `token-name: el2ck_token` + `is-read-cookie: true`，并保留 CSRF 校验。

### 6.2 登录/登出

- `AuthController.login`：校验密码后 `StpUtil.login(user.getId())`，返回 `{ token, userId, username, role, mustChangePassword, capabilities }`；
- `logout`：`StpUtil.logout()` + `AuthContext.clear()`；
- `/api/me`：从 `StpUtil` 取 userId，再查用户与权限返回。

### 6.3 拦截器（替代 SessionAuthFilter）

顺序：

1. 未登录 → 401（`/api/login`、`/api/csrf`、`/api/health` 放行）；
2. 查用户不存在 → 踢下线 + 401；
3. `enabled=false` 或 `auth_version` 不匹配 → 踢下线 + 401；
4. 登录超过 12 小时 → 踢下线 + 401；
5. `must_change_password=true` → 仅放行 `/api/me`、`/api/me/password`、`/api/logout`，其余 403；
6. `AuthContext.set(userId, username, role)`；
7. 功能权限校验（见 6.4）。

### 6.4 功能权限

实现 `StpInterface`：

```java
public List<String> getPermissionList(Object loginId, String loginType) {
    // 按 userId 查 el_user_roles → el_role_permissions → el_permissions.code
    // 进程内缓存（如 Caffeine / 简单 Map + TTL 60s），角色变更时主动失效
}
```

两种校验方式（二选一或混用）：

- **注解**：接口方法上加 `@SaCheckPermission("sync:run")`；
- **拦截器映射**：在配置里维护“路径 + 方法 → 权限点”表，集中管理。

建议：核心写操作（增删改、运行、导出）用注解；只读列表用拦截器映射，避免每个 Controller 都加注解。

### 6.5 数据权限

保持现有实现：

- `ResourceAccessService`：`requireOwner`、`hasGrant`、`visibleTables`、`visibleDatabases`；
- `SyncAccessService`：同步任务的源/目标访问；
- `CkAccessProvisioner`：ClickHouse 真实用户授权。

改造只做一件事：把 `AuthContext.userId()` 的来源从 Spring Security 换成 Sa-Token（由拦截器填充），业务代码不变。

### 6.6 登录限流与审计

- 限流：保留 `AuthController` 的内存 Map（单实例有效）；多实例时再换 Redis/DB；
- 审计：登录成功/失败、登出、权限拒绝写入 `el_access_audit`（现有表），补 `action` 类型。

## 7. 前端改造

| 位置 | 改动 |
|---|---|
| `web/src/api/http.ts` | 请求拦截器加 `Authorization: Bearer <token>`；移除 CSRF 逻辑（Header 方案） |
| `web/src/stores/auth.ts` | token 存 `sessionStorage`（或内存 + 刷新时用 refresh token）；`restore()` 改为校验 token |
| 登录页 | 响应结构适配；登录失败提示保持不变 |
| 路由守卫 | `canAccess` 从“角色白名单”改为“权限点判断”（`me.permissions` 返回权限点列表） |
| 菜单/按钮 | 新增 `v-permission="'sync:run'"` 指令或 `hasPerm()` 方法，统一控制显示 |
| 登出 | 调 `/api/logout` 后清 token |

权限点获取：`/api/me` 返回 `permissions: string[]`，前端缓存到 Pinia；路由切换时按权限过滤菜单。

## 8. 迁移步骤（可分阶段上线）

**阶段 0：准备**

1. 新增 `docs/mysql/2026110x_roles_permissions.sql`（4 张表 + 初始数据）；
2. 在 212 执行，核对表结构；
3. 保留旧登录代码，新登录用开关切换（如 `app.auth.framework=sa-token|legacy`）。

**阶段 1：后端接入**

4. 引入 Sa-Token，实现登录/登出/me；
5. 实现拦截器与 `StpInterface`，`AuthContext` 保持不变；
6. 用注解/拦截器替换 `RoleAuthFilter` 的硬编码规则；
7. 单测：登录、禁用、改密、超时、权限拒绝、数据权限。

**阶段 2：前端切换**

8. `http.ts` 改为 token 认证；
9. `auth.ts` 权限点化，路由守卫与菜单改用权限点；
10. 登录页与登出适配。

**阶段 3：清理**

11. 删除 `spring-boot-starter-security`、`SecurityConfiguration`、`SessionAuthFilter`、`SessionIdentity`、`BasicAuthFilter`；
12. 更新 `docs/`（部署说明、MySQL 说明、README）；
13. 回归测试后删除开关与旧代码。

**回滚**：阶段 1、2 保留开关；回滚时切回 `legacy` 并保留旧表结构。

## 9. 测试与验收

| 层级 | 用例 |
|---|---|
| 单元测试 | 登录成功/失败、禁用、`auth_version` 变化、12 小时超时、强制改密、权限点解析 |
| 接口测试 | 无 token 401、无权限 403、有权限 200、登出后 token 失效 |
| 数据权限 | 跨用户访问他人表/任务/连接被拒；共享后可见 |
| 页面级（Playwright） | 不同角色登录后菜单/按钮可见性、直接访问受限路由被拦、改密后强制跳转 |
| 回归 | 同步任务、数据源、工作流、SQL 查询、导出等主流程 |

## 10. 风险与注意事项

1. **CSRF**：token 放 Header 可移除 CSRF；放 Cookie 必须保留 `SameSite` + CSRF 校验。
2. **token 存储**：`sessionStorage` 刷新丢失（可接受，重新登录）；若放 `localStorage` 需评估 XSS 风险。
3. **并发登录**：`is-concurrent` 决定是否允许同账号多端；与“强制下线”需求一起确认。
4. **权限缓存**：`StpInterface` 查库要加短 TTL 缓存，角色/授权变更时主动失效，避免撤权延迟。
5. **强制改密**：现有规则必须完整迁移，否则会绕过首次改密。
6. **`auth_version`**：改密/禁用必须递增，否则旧 token 仍有效。
7. **审计**：登录失败、权限拒绝要留痕，便于排查。
8. **密码策略**：沿用现有加盐 SHA-256；如要升级到 BCrypt，需在登录时做一次透明迁移。

## 11. 明确不做

- 不引入 Redis（单实例阶段）；
- 不做多实例会话共享；
- 不做 SSO/OAuth2（后续需要时再评估 Keycloak）；
- 不改变 ClickHouse 表级授权的实现（`CkAccessProvisioner` 保持）。
