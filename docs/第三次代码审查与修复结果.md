## 补充复核问题及本轮修复

以下保留发现问题时的触发条件，并说明本轮修改。自动化使用本地 H2 与执行锁替身，不声称已在 212 复现或验证真实 MySQL 多实例故障。

### P1：数据源删除与新增/改绑任务没有共同的互斥边界

**本轮已修复。** 删除、新增/改绑同步任务及新增/更新工作流共用数据源与所有权行的 `SELECT ... FOR UPDATE`，锁持有至事务提交。删除事务显式采用 `READ_COMMITTED`，取得源锁后以普通查询读取最新已提交的引用，并清除 MyBatis 本地缓存，不锁整张任务/工作流表。若被外层其他隔离级别事务包裹则明确拒绝，避免旧快照漏检。多个工作流源按 ID 升序取锁；非法源节点及已删除/非本人数据源拒绝保存。

`DataSourceReferenceConcurrencyTest` 使用两个独立事务连接，覆盖创建先行、删除先行、改绑双方先行、创建/删除回滚、工作流引用、相反源顺序、无关写入不阻塞及拒绝外层旧快照事务。夹具删除了生产不存在的数据源索引，明确配置隔离级别。H2 验证事务等待和最终引用完整性；真实 MySQL 加锁和隔离行为仍需实库验收。

- 位置：`MetadataRepository.deleteDataSource()`（约 519 行）、`createSyncTask()`（约 128 行）、`updateSyncTask()`（约 144 行），以及 `SyncAccessService.persist()`（约 113 行）。
- 修复前删除先扫描引用，随后才删除；任务保存只校验所有权，没有锁住被引用的数据源行。`persist()` 锁定的是目标资产，不是源数据源。数据源删除与任务创建又在不同 Service 中，因此单实例的并发请求也可能交错。
- 触发顺序：删除事务确认无引用 → 另一请求通过源所有权校验并保存任务 → 删除继续提交。当前没有源外键兜底，可能留下指向已删除数据源的任务；新增工作流中的同类引用也需一起纳入保护。
- 建议：删除和所有引用写入在同一数据源锁下完成，锁内重新确认源存在、权限及引用。引用检查使用能看到最新提交结果的读取方式，不能仅加一个锁却继续使用旧事务快照。多源工作流按固定顺序取锁，避免死锁。
- 验收：用两条独立事务连接覆盖“删除先行”“创建先行”和“任务改绑”三种交错；最终只能删除成功或引用保存成功，不能同时留下悬空引用。

### P1：同步任务修改/删除没有参与执行锁

**本轮已修复。** 启动、修改、删除和启停开关共用 `SyncExecutionGuard` 的任务级会话锁。启动取锁后重新读取配置、启用状态和权限；修改/删除等到持久化方法返回、事务提交后才释放。正在运行时修改、删除或切换启用状态返回 409；取消执行仍走独立取消接口。

编辑任务的源结构/目标字段探测移至执行锁外，并移除更新方法的 JVM 全方法同步，避免远端慢查询占住执行入口。提交阶段仍保留即时权限、源行锁及目标资产登记校验；如果此时已有运行取得执行锁，编辑会明确冲突，不覆盖执行中的配置。

`SyncTaskMutationLockTest` 用两个独立 Service 实例和共享锁替身，验证执行中冲突、更新/删除持锁至提交返回、锁内重新读取配置/权限，以及失败释放。现有 `SyncExecutionGuardTest` 验证 JDBC 锁占用、失效和关闭失败路径；这些测试不替代真实 MySQL 命名锁联调。

- 位置：`SyncService.update()`（约 549 行）、`delete()`（约 579 行）、`startRun()`（约 695 行）。
- 修复前启动通过 `SyncExecutionGuard.reserve()` 获取跨实例锁；修改和删除仅使用 JVM 内 `synchronized` 及 `hasRunningSyncRun()`。两个实例可能在“检查无运行记录”和“写入 running”之间交错，导致运行中的任务配置或断点被修改/删除。
- 修复前启动先读取任务快照，后获取执行锁。因此仅给修改/删除加锁还不完整：启动也应在取锁后重新读取任务、检查启用状态和权限，不能使用锁外已经过期的配置。
- 建议：启动、修改、删除共用任务级执行锁，并持有到各自提交/收尾结束。单实例当前的 `synchronized` 能限制同一 Service 的并发，多实例部署前应补齐数据库侧互斥。
- 验收：两个实例同时启动与修改/删除同一任务时，一方明确冲突；已启动任务的配置、运行历史和断点保留到结束。

### P2：进度轮询查询量随全部任务数增长

**本轮已修复。** 任务定义、源/连接名称及断点、最近运行分别批量查询，非空列表固定 3 条 SQL，空列表 1 条；每条 SQL 均限定当前用户所有权，源名称另校验源所有权，不读取源配置或连接密码。原始断点只用于生成展示 DTO。

页面每两秒只查正在观察的 `taskId/runId`；运行结束才共享刷新任务列表和断点。保留旧后端的历史查询回退、4xx 停止与网络故障有限退避。慢列表不能覆盖更新的进度，旧观察的迟到错误不能停止新的观察；终态后的附属刷新失败单独提示。

- 位置：`MetadataRepository.listSyncTasks()`、`listLatestSyncRuns()`、`SyncService.list()/toDTO()`、`SyncTasksView.vue` 的 `loadShared()`。
- 修复前列表逐个读取任务和最新运行，再逐个读取断点、数据源及连接。前端运行时每两秒刷新整份列表；同一浏览器共享请求只减少重复 HTTP 请求，没有消除后端的逐任务 SQL。
- 影响：任务较多或多个页面同时观察时，会增加元数据库负载和进度刷新延迟。目前未做生产规模压测，不把这一推断表述为已测得的性能故障。
- 建议：按当前用户可见任务 ID 批量读取摘要，并让运行期间只查询正在观察的 runId；历史列表按需刷新。不得直接改成不带权限范围的全库查询。
- 验收：记录 100/1000 个任务、1/3 个运行任务下每轮 SQL 数量及耗时，证明查询量不再与全部任务数线性增长。

历史基础表的类型、默认值和索引契约尚未完整覆盖，继续列为后续加固项；目前已覆盖表名、所需列、关键新增字段、部分基础身份字段及关键索引/事务表引擎，不应描述成“完整校验所有表结构”。

## 后续优化与最新验证（2026-10-31 复核）

### 同一目标表的别名冲突与锁等待

之前 `SyncAccessService.uniqueTarget()` 只比较 `connection_id`，同一已登记物理实例的两个连接别名可以绕过目标表冲突检查；`persist()` 等待资产锁后又可能继续使用先前建立的事务快照。

现在按已登记的 `ck_instance_id` 合并连接别名的目标范围，同一实例、同一库表只允许一个同步任务使用。不同实例的同名表、编辑当前任务及不同数据库仍允许。冲突检查覆盖所有所有者，但只返回统一提示，不暴露其他用户的任务详情。

保存事务显式使用 `READ_COMMITTED`，锁定目标资产后重查冲突和权限。目标在等待期间被删除、改名或转移归属会拒绝保存，不能沿用旧授权；锁一直持有至事务提交。抽取 `MetadataTransactions` 供目标保存与源删除共用实际隔离级别校验，拒绝加入旧快照事务。

若历史数据已经存在通过多个连接别名指向同表的任务，新版会提示目标冲突，需要人工保留一个任务或修改目标；不会自动删除旧任务。

### 关键结构预检

新增 `metadata-critical-indexes.yaml`，检查既有结构的 17 项关键索引约束，以及相关 13 张表的 InnoDB 引擎；补齐基础身份/归属字段的类型和可空性检查。允许索引改名、等价唯一键列顺序，以及查询索引追加覆盖字段；拒绝用普通索引、字符串前缀或增加其他列的唯一键代替完整唯一约束。

## 定时同步与异常恢复修复（2026-10-31）

### 过期定时回调和调度恢复

原来的调度器只在回调结束时检查排程是否仍有效，触发入口按任务 ID 直接启动；在两次调度扫描之间把任务改为手动或修改 Cron，旧回调仍可能创建运行记录。现在先检查内存中的排程身份，再将排程时的 Cron 交给 `SyncService`，取得任务会话锁后重新读取任务，校验启用状态、调度类型和 Cron，然后才创建运行记录。配置在取锁前变化会跳过旧触发，五段 Cron 与补齐秒位的六段写法继续兼容。

另修复两处排程生命周期问题：

- Cron 变成非法值时，必须删除已经取消的旧条目，否则再改回原值会被误判为无需排程，任务不再触发。新表达式没有下次执行时刻时也清理旧条目。
- 关闭调度器时先禁止新排程，再取消和清理条目。执行中的旧回调不能重新提交任务；过期回调也不能覆盖新的 Cron。实际启动在调度表锁外执行，缓慢启动不阻止其他线程调整排程。

XXL-JOB 仍通过原有的单参数入口按任务 ID 启动，由调度中心控制触发时间；本次配置快照复核仅用于应用内 Cron 回调。手动执行仍可启动已启用的手动任务。没有增加数据库字段或修改 HTTP 接口。

### 异常运行记录独立恢复

此前一轮恢复把所有任务放在同一个异常处理块中，某个任务取得锁或更新状态失败会使后续任务都跳过。现在分别记录扫描失败和单个任务恢复失败；一个任务失败后继续处理其余任务，下一轮重试失败任务。扫描增加 5 秒 JDBC 查询超时。

仍必须先取得该任务的 MySQL 会话锁并确认锁有效，才将其遗留的 `running` 记录收尾；正在被其他实例执行的任务会跳过。用户主动启动时，如果遗留状态恢复失败仍拒绝启动并释放会话，不能把定时恢复的错误隔离变成忽略启动失败。

## 同步取消与关闭流程优化（2026-10-31）

### 执行和收尾之间的取消边界

原实现只用线程中断表达取消：驱动消费中断标记后，取消原因可能丢失；执行结束到结果写库之间，重复取消或已经开始的超时回调又可能重新设置中断，干扰 MySQL 取连接及状态收尾。

新增 `SyncWorker` 保存本轮取消原因，并让取消和进入收尾使用同一个监视器。首次原因优先，重复请求不再反复中断驱动清理；开始收尾后拒绝新的中断请求。引擎执行检查同时校验取消原因与会话锁，驱动清除中断标记不能取消已受理的停止请求。驱动收到取消后即使返回统计，本轮也不会误报成功，已取得的读写行数继续保留。

手动取消、超时和服务关闭分别记录明确原因。`runWorker` 统一处理身份解析、定时器建立、业务执行及结果保存的失败路径，退出时清理超时任务、释放会话锁及并发名额。总超时为 0 时不创建定时器。

### 服务关闭和工作线程登记

关闭先设置拒绝新执行的状态，再取得已登记线程的快照；工作线程登记与启动使用相同的短锁，锁内不执行远程检查或 SQL。正在做预检的请求在检查结束后返回 503；如果关闭恰好发生在运行记录创建期间，则不启动引擎，并在释放任务锁前尝试把该记录收尾为失败。

线程登记保留至结果写库和会话锁释放完成。关闭只中断仍在执行的任务，收尾中的线程继续完成清理；不再因过早删除登记而漏掉等待。关闭等待仍有原先的 45 秒上限，不强制终止不响应中断的驱动。进行中的启动请求或收尾遇到数据库关闭、断网时，仍可能留下 `running`，由会话锁恢复机制后续处理。

取消接口字段保持不变。`cancelled=false` 表示本次未提交取消请求，可能是本实例没有执行线程、其他实例正在执行，或任务已进入收尾；前端改为提示“未提交取消请求，请刷新查看任务状态”，不再断言任务没有运行。本次没有实现跨实例取消，也不撤销已确认写入或删除断点。

## SFTP 断点内容校验修复（2026-11-02）

本节替代上文 2026-10-31 记录中的首尾样本校验策略。旧实现只比较首尾各 64 KiB，
如果远端文件只修改中间内容且大小、mtime 不变，在尚无可信完整摘要时会接受旧前缀，
也可能复用已经下载完成但尚未保存摘要的旧缓存。

- 恢复下载前改为逐块比较整个已下载前缀；发现不一致时从 0 下载，避免拼接新旧内容。

## 默认续传与失败后的操作入口（2026-11-02）

按用户明确的操作语义统一执行入口：普通“执行”默认优先使用已有断点；发生可恢复的传输故障时，

  超时、取消等全部失败，不再仅靠错误信息中的“中断”等关键词决定是否显示。
- “继续传输”调用普通 `/run`，保留并优先使用已有断点，没有断点时从头开始。
- “重新传输”确认后调用 `/restart`，替换旧断点并全量重建目标数据；确认框说明会清空现有目标数据，
  任务配置与执行历史保留。取消确认不会发起任务或删除操作。
- 新运行已启动或已有更新的成功记录时不再显示旧失败恢复入口；停用任务的按钮禁用。
- 服务层规范本次执行快照为启用续传，兼容历史 `resumable=0` 的记录，与现有新建/编辑及 DTO 的默认行为一致。
