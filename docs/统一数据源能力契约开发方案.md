# 统一数据源能力契约开发方案

版本：V1.0（建议稿）  
日期：2026-10-26  
适用项目：`E:\wenjian\el\el-to-ck-java`  
范围：数据源管理、映射同步及相关前后端接口。

本文是开发方案，尚未实施代码改造。接口、类名和新增字段均为建议定义，示例不是当前接口返回值。

## 1. 要解决的问题

当前同一种数据源是否可用，由多个位置分别判断：

| 位置 | 当前职责 | 容易出现的问题 |
| --- | --- | --- |
| `DataSource.validType()` | 判断合法数据源类型 | 合法保存不等于支持同步 |
| `DataSourceService` | 配置、连接、对象、字段、预览分发 | 各功能可能接入不完整 |
| `SyncService` | 同步源与模式校验 | 保存接口与执行支持范围不一致 |
| `SyncEngine` | 按类型选择读取及执行链路 | 运行时才发现未支持 |
| `DataSourceFormDialog.vue` | 类型入口与表单 | 类型和禁用状态另有一份列表 |
| `SyncTasksView.vue` | 数据源过滤、对象选择、字段读取、策略选项 | 页面隐藏了实际上已支持的源 |

Kafka、Hive 曾出现“创建并绑定 admin 成功，但新增同步映射中选不到”的问题。原因是管理、页面筛选、保存和执行分别维护支持列表，没有统一约束。

**本方案目标：同一份服务端能力定义，同时约束页面展示、管理接口、任务保存和运行入口。注册了一个类型，不代表自动获得全部能力；声明一种能力，必须有对应实现。**

## 2. 目标与边界

### 2.1 必须达到的结果

1. 数据源类型只在统一注册中心声明一次，前端不再维护同步类型白名单。
2. “能创建”“能探测字段”“能全量同步”“能增量同步”分别声明，不能相互推导。
3. 同步保存与运行使用同一个能力判定器。
4. 类型能力与实现绑定不一致时，在启动阶段失败，不等到用户执行任务。
5. 页面能说明不可选原因，后端仍独立鉴权和校验。
6. 已有任务、类型值、加密配置和权限规则保持兼容。
7. 新增来源有固定接入清单，能够证明管理到执行的链路完整。

### 2.2 本次不扩展的业务范围

首轮仍使用 Java 8、Spring Boot 2.7、现有 MySQL 元数据和 ClickHouse 目标端。不引入动态上传插件、分布式执行器或 CDC，也不因统一契约就开启 Hive/Kafka 增量。

首轮服务于**映射同步**。通用 DAG、仲裁、任意 SQL 查询是不同使用场景，不能将“支持映射同步”自动推广到这些入口。

## 3. 核心原则：三层信息分别表达

### 3.1 类型能力：这个适配器实现了什么

类型级、服务版本内确定，不依赖某一条数据源连接是否在线。

例如：Kafka 支持列举 Topic、探测 JSON 字段、全量快照；当前没有增量或持续消费执行器。

### 3.2 使用条件：当前配置和任务是否满足要求

实例级或任务级，可能与源对象、增量字段、目标连接有关。

例如：MySQL 类型支持增量，不代表每张表都有可用的分页主键；Kafka 类型支持字段探测，不代表空 Topic 能自动识别结构；库内表源需要目标连接上下文。

这类条件分为：

- **静态检查**：配置字段是否齐全、模式是否支持、对象是否已选择。
- **远端检查**：连接是否可用、表是否存在、实际字段和主键是否满足要求。

列表接口只做静态判定，不逐条访问远端服务。远端失败由探测、保存校验和运行预检返回，不能伪装成类型不支持。

### 3.3 用户权限：当前账号是否允许操作

权限继续由现有 `ResourceAccessService`、`SyncAccessService`、真实 CK 身份和文件访问规则决定。

**有能力 ≠ 有权限；有权限 ≠ 源在线；源在线 ≠ 所有表可同步。**

类型描述可以在已登录用户范围内共享；实例能力接口必须先验证资源归属，不能向其他用户泄露对象、配置或可用性信息。

## 4. 建议总体结构

```text
                    SourceRegistry（服务端唯一注册中心）
                                  │
                  ┌───────────────┼────────────────┐
                  ↓               ↓                ↓
          SourceDescriptor   MetadataAdapter   ExecutionBinding
          类型/展示/能力声明   配置/连接/对象/字段   模式→执行实现
                  │               │                │
                  └───────────────┼────────────────┘
                                  ↓
                      SourceCapabilityService
                  合并类型声明、实例条件、场景约束
                                  │
               ┌──────────────────┼───────────────────┐
               ↓                  ↓                   ↓
           前端类型与向导      保存/探测接口         执行入口复查
                                                  │
                                                  ↓
                                      现有映射/类型/手机号校验
                                                  ↓
                                      现有 CK 写入与生命周期
```

注册中心负责“有哪些能力和实现”；能力服务负责“本次请求允许使用哪些能力”；适配器负责“如何访问源”。用户归属、凭据管理、手机号政策、目标建表和写入仍由公共服务负责。

## 5. 契约模型

### 5.1 SourceDescriptor：类型描述

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `type` | 持久化类型标识，保持现有值 | `pgsql`，不改成 `postgres` |
| `displayName` | 展示名称 | PostgreSQL |
| `category` | 来源分类 | FILE / DATABASE / DOCUMENT / MESSAGE |
| `iconKey` | 前端图标标识，不能是可执行 HTML | kafka |
| `formKey` | 已注册的前端配置表单标识 | kafka / hive / sql / local_file |
| `createPolicy` | 新增入口是否开放及原因 | ENABLED / DISABLED |
| `objectSelection` | 对象选择规范 | TABLE / COLLECTION / TOPIC / FILE / DIRECTORY / FIXED |
| `metadataCapabilities` | 支持的元数据操作集合 | TEST_CONNECTION / LIST_OBJECTS / DESCRIBE_SCHEMA |
| `syncBindings` | 同步模式与执行器绑定 | full → kafka_snapshot |
| `readSemantics` | 读取语义 | FINITE_SNAPSHOT / FILE_SCAN / DIRECTORY_CHANGES |
| `schemaDiscovery` | 字段来源与采样说明 | DECLARED / INFERRED / TASK_SELECTED |
| `constraints` | 已实现的明确约束 | 需要增量字段、目标上下文等 |
| `warnings` | 影响使用决策的说明 | “重复快照会重读保留数据” |

模式沿用现有 `full`、`incremental`，不更改任务持久化值。`syncBindings` 非空才表示支持映射同步，不另设容易与它冲突的 `supportsSync` 布尔。

**新增入口与执行能力独立。** `clickhouse`、`ck_table` 当前在新增页面禁用，但已有记录仍能用于同步；`json`、`xlsx` 当前没有同等新增卡片，也不应因此拒绝已有任务。

### 5.2 ObjectSelection：对象选择规范

建议包含：

```json
{
  "kind": "TOPIC",
  "selectionMode": "PICK_ONE",
  "required": true,
  "defaultConfigKey": "topic",
  "label": "源 Topic",
  "placeholder": "选择 Topic"
}
```

区别说明：

- `PICK_ONE`：表、集合、Topic。
- `CONFIGURED`：来源已由配置绑定，例如本地文件路径。
- `DIRECTORY_RULE`：SFTP 目录、匹配规则及任务选定结构。
- `FIXED`：库内 CK 表，库表来自数据源配置，并需要目标连接提供业务身份。

表名、集合名、Topic 名和文件路径不能共用一个 SQL 标识符正则，必须由对应适配器校验。

### 5.3 SourceAvailability：实例可用能力

用于在当前用户有权访问的前提下说明可用模式及限制：

```json
{
  "dataSourceId": 28,
  "type": "kafka",
  "useCase": "MAPPING_SYNC",
  "selectable": true,
  "allowedModes": ["full"],
  "issues": [],
  "remoteCheck": "NOT_CHECKED"
}
```

`issues` 结构建议为 `{reasonCode, field, message}`，例如：

- `CONFIG_INCOMPLETE`：缺少连接参数。
- `SOURCE_CONTEXT_REQUIRED`：需要选择目标连接才能读取源。
- `SOURCE_MODE_UNSUPPORTED`：不支持请求模式。
- `SOURCE_OBJECT_REQUIRED`：尚未选择对象。
- `SOURCE_IMPLEMENTATION_MISSING`：实现缺失；正常服务启动后不应出现。

`selectable=false` 只用于无法在当前选择步骤解决的问题，例如该类型不支持当前场景或保存配置缺失关键连接信息。选择表、设置增量字段等本来就在后续步骤完成的事项，可以作为下一步要求，不能导致用户一开始就无法选源。

对于无权访问或不存在的数据源，返回现有 404 语义，不返回包含细节的 `issues`。

### 5.4 SchemaResult：字段结构说明

保留现有 `Column.name/type`，在新接口中增加结构来源信息：

```json
{
  "columns": [{"name": "phone_md5", "type": "String"}],
  "origin": "INFERRED",
  "sampleLimit": 100,
  "complete": false,
  "warnings": ["字段由前 100 条 JSON 消息发现，后续消息可能出现新字段"]
}
```

`complete=false` 表示不能保证穷举字段，不表示字段读取失败。空 Topic 等无法识别字段的情况应明确失败，不伪造空结构为“可直接同步”。

## 6. 接口设计与职责

### 6.1 Java 接口建议

以下为签名级示意，使用 Java 8 普通类/枚举，不使用 record、sealed class 或 Java 17 API。

```java
public interface SourceMetadataAdapter {
    void validateConfig(SourceConfig config);
    void testConnection(SourceContext context);
    List<SourceObject> listObjects(SourceContext context);
    SchemaResult describe(SourceContext context, SourceSelection selection);
}

public interface SourceReader extends AutoCloseable {
    SourceSchema schema();
    SourceBatch next(int maxRows);
    OptionalLong estimatedRowCount();
    void close();
}
```

这里的元数据接口是能力集合示意：实现时可拆成 `ConnectionTester`、`ObjectLister`、`SchemaDescriber` 等小接口，注册对象只持有实际实现的操作。**不以默认空列表、默认成功或统一 UnsupportedOperationException 冒充已支持能力。**

注册条目建议为不可变对象：

```text
SourceRegistration
  descriptor
  metadataOperations : 操作 → 对应实现
  syncBindings       : 模式 → 执行策略引用
```

`metadataCapabilities` 从已绑定操作推导；支持的同步模式从已绑定执行策略推导。描述中如保留相同字段用于接口输出，也必须由注册对象生成，避免“声明一份、绑定另一份”。

### 6.2 SourceReader 的严格要求

1. 使用游标式 `next(maxRows)`，对调用方隐藏 SQL、OFFSET 和 keyset 差异。
2. `SourceBatch` 必须有 `rows` 和 `endOfInput`；**不足一批不必然等于结束**。新统一执行器按显式结束信号判断，旧 PageSource 迁移时先保留原语义并逐源验收。
3. 列顺序在同一次读取会话内固定，行宽与结构一致；额外字段、缺字段按类型适配器明确的政策处理。
4. 第一轮维持已有字符串单元格协议，区分 `null` 与空字符串，保留 Decimal、整数和小数秒精度；不借此改为 double 中转。
5. 增量过滤由结构化 `ReadRequest` 表达，包括字段、类型、初始水位；SQL 由适配器生成，前端不能提交任意 WHERE。
6. 初始水位在运行准备阶段确定；不能每批重新读取目标最大值改变本次过滤边界。
7. `estimatedRowCount()` 可返回未知，不得为获取行数而消费掉不可重读的流，也不要求每次执行昂贵 COUNT。
8. `close()` 在成功、异常和取消路径均执行；读取必须响应取消信号及超时。
9. 结构和读取边界在运行会话内确定。Kafka 运行尽量在同一个会话中探测/固定结构并保留采样批次，避免采样与正式读取来自不同保留边界；这是后续提取 Reader 时的明确改造项。

### 6.3 SourceContext 的内容与权限边界

建议包含：当前用户 ID、源 ID、运行 ID、取消/超时信息，以及可选目标连接 ID。凭据由服务端在鉴权后解析到内部对象，不通过 HTTP 下发，不写入执行计划日志或前端缓存。

SourceContext 不自行决定“谁是当前用户”。请求入口使用现有认证上下文；定时任务使用现有任务所属用户恢复逻辑。来源插件无权回退管理账号读取业务数据。

库内 CK 表继续通过真实 CK 用户身份读取，不能为统一接口改成数据源保存的公共账号。

### 6.4 特殊链路：SFTP 不强行塞进普通 Reader

SFTP 目录涉及枚举、结构分类、按文件去重、变化文件删除旧数据、逐文件失败统计、强制重建。仅有 `next()` 无法完整表达这些行为。

因此同步执行策略区分：

- `ROW_TRANSFER`：普通行批次读取，进入公共映射与写入链路。
- `DIRECTORY_SYNC`：保留专门的目录编排策略，目录内每个文件仍复用文件 Reader 和公共校验。

统一的是能力解析和策略选择，不是把全部来源改写成相同业务流程。系统字段 `path`、文件去重记录和“排除但保留旧数据”等语义必须保留。

## 7. 当前类型的第一版能力矩阵

下表是按当前源码建议的初始映射。实施时逐个核对并作为注册清单，不直接扩展现有能力。

| 类型 | 新增入口 | 选源方式 | 管理能力 | 映射同步模式 | 特殊条件/语义 |
| --- | --- | --- | --- | --- | --- |
| csv | 开放 | 配置文件 | 文件有效性、结构、预览 | full / incremental | 上传归属、解析设置、增量类型约束 |
| json | 当前不提供新增卡片 | 配置文件 | 文件有效性、结构、预览 | full / incremental | 保留已有记录及任务 |
| xlsx | 当前不提供新增卡片 | 配置文件 | 文件有效性、结构、预览 | full / incremental | 经现有 Excel 转换路径读取 |
| sftp | 开放 | 目录规则 | 连接测试、目录浏览、结构分类 | full | 执行策略 DIRECTORY_SYNC；按文件变化处理，不是行水位增量 |
| mysql | 开放 | 表 | 连接、对象、结构 | full / incremental | 现有读取链路要求可用单列主键安全分页 |
| pgsql | 开放 | 表 | 连接、对象、结构 | full / incremental | 保持现有主键及时间精度约束 |
| clickhouse | 当前新增卡片禁用 | 表 | 连接、对象、结构 | full / incremental | 已有源可用；独立读取游标 |
| mongodb | 开放 | 集合 | 连接、对象、嵌套字段探测 | full / incremental | 采样结构、源端水位条件、精度检查 |
| ck_table | 当前新增卡片禁用 | 配置库表 | 对象存在、结构（依赖目标连接） | full / incremental | 当前用户 CK 身份，源目标不能相同 |
| hive | 开放 | 表 | 连接、对象、结构 | full | 现有 HiveServer2 JDBC；不开放增量 |
| kafka | 开放 | Topic | 连接、对象、JSON 字段采样 | full | 有界快照；不提交位点；不开放持续消费/增量 |

SFTP 旧单文件兼容路径可以注册为 `LEGACY_FILE` 选择变体，仅服务已有任务；新增任务仍走当前目录规则。不能因旧分支存在就擅自开放新产品入口。

本地文件的“连通性测试”应表达为文件可读取/格式有效，不能在页面显示成数据库连接在线。

## 8. HTTP 接口建议

### 8.1 类型目录

`GET /api/datasource-types?useCase=MAPPING_SYNC`

新增 `DataSourceTypeController`，避免将类型目录路径误当成数据源 ID。它返回当前版本的类型描述、操作及模式能力，不访问任何远端来源。

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "contractVersion": 1,
    "catalogVersion": "source-catalog-v1",
    "types": [{
      "type": "kafka",
      "displayName": "Kafka",
      "formKey": "kafka",
      "createPolicy": {"enabled": true},
      "objectSelection": {"kind": "TOPIC", "selectionMode": "PICK_ONE", "required": true, "defaultConfigKey": "topic"},
      "metadataCapabilities": ["TEST_CONNECTION", "LIST_OBJECTS", "DESCRIBE_SCHEMA"],
      "syncModes": ["full"],
      "readSemantics": "FINITE_SNAPSHOT"
    }]
  }
}
```

### 8.2 实例能力

首轮在现有 `GET /api/datasources` 的 DTO 中增量添加 `availability`、`capabilityVersion`，列表一次返回，避免每条记录单独请求。字段可为空以兼容旧客户端。

对于需要任务上下文的详细判定，增加：

`GET /api/datasources/{id}/capabilities?useCase=MAPPING_SYNC&targetConnectionId=...`

该 GET 只做归属、角色和配置条件检查，不探测远端。目标连接也必须校验当前用户可用，不能信任传入 ID。

### 8.3 保留现有元数据接口

现有 `/{id}/objects`、`/{id}/columns`、`/test`、`/{id}/test`、`sql-tables`、`sql-columns` 和 SFTP 接口先保持响应形状，内部逐步委托注册适配器。

新的结构说明可放在新增 `POST /{id}/schema` 接口中返回 SchemaResult；旧 `/columns` 仅投影成原数组，不能原地把数组改成对象。

通用 `objects` 可增量接受 `targetConnectionId`，处理库内 CK 表的上下文需求；不需要此上下文的类型忽略它，不能因此切换到目标端凭据读取外部来源。

### 8.4 任务验证

任务创建/更新继续使用现有接口。保存流程与运行流程调用同一个：

```text
SourceCapabilityService.requireSupported(type, useCase, mode, selection)
```

保存时读取最新源/目标结构，执行时再次校验权限、结构和能力，避免任务保存后配置或权限变化。

### 8.5 错误响应兼容

当前 `ApiResponse.code` 是数字 HTTP 状态语义。新增机器可读原因时，只增加可选 `reasonCode` 和安全 `details`，保留原 `code/message`。

示例：

```json
{
  "code": 400,
  "message": "Kafka 当前仅支持全量快照同步",
  "reasonCode": "SOURCE_MODE_UNSUPPORTED",
  "details": {"type": "kafka", "requestedMode": "incremental", "allowedModes": ["full"]}
}
```

401、403、404、远端故障及配置错误继续区分，不统一包装成“类型不支持”。不得返回密码、完整连接串、管理身份或第三方原始堆栈。

## 9. 后端改造位置

建议新增结构：

```text
service/datasource/capability/
  SourceRegistry
  SourceRegistration
  SourceCapabilityService
  SourceDescriptorValidator
service/datasource/adapter/
  LocalFileSourceAdapter
  SftpSourceAdapter
  SqlSourceAdapter
  MongoSourceAdapter
  CkTableSourceAdapter
  HiveSourceAdapter
  KafkaSourceAdapter
entity/datasource/capability/
  SourceDescriptor / SourceAvailability / SourceSelection
  SchemaResult / SourceIssue / 相关枚举
sync/source/                          # Reader 提取阶段再新增
  SourceReader / SourceBatch / SourceReadRequest
  现有读取实现的适配层
```

| 现有文件 | 具体改法 |
| --- | --- |
| `DataSource.java` | 类型字符串常量保留；服务端合法类型校验迁到 Registry，避免实体静态方法持有 Spring 容器 |
| `ServiceConfiguration` | 注册适配器和 Registry，注入能力服务；避免适配器依赖 DataSourceService 又被其反向调用 |
| `DataSourceService` | 保留归属、加解密、密码沿用、去重、文件权限；配置/元数据操作委托适配器 |
| `DataSourceDTO` | 添加实例可用能力，不加入解密凭据 |
| `SyncService` | 用共享判定器替换支持类型/模式名单；保留映射、目标权限及结构校验 |
| `SyncEngine` | 第一阶段保留读取实现，第二阶段接注册执行绑定，后续提取 Reader；保留公共写入校验 |
| `SqlSourceCatalogController` | 旧包装协议保留，内部转发统一能力；不扩大 SQL 查询范围 |
| `DataSourceStatusService` | 根据已绑定测试操作执行状态检查，不另写类型支持名单 |
| `ResourceBoundaryInterceptor` | 为新增类型目录控制器显式放行已登录业务用户；实例接口继续归属校验 |

**消除循环依赖的约束：** 适配器可以依赖底层 DbSource、Duck、Kafka/Hive 工具及必要身份解析服务，不能回调 DataSourceService 的同名方法。需要提取公共辅助类时按底层依赖方向处理。

## 10. 前端改造

### 10.1 数据源新增页面

用类型目录生成类型卡片。`createPolicy` 控制可创建性，表单通过本地受控的 `formKey → Vue 组件` 映射渲染。

首轮保留专用表单，不做服务端下发任意 Vue 模板或全动态 JSON 表单。遇到未知 `formKey`，显示“当前页面版本暂不支持此配置”，禁用创建，不能提交缺少配置的对象。

### 10.2 新增同步映射

删除 `dss.filter(d.type === ...)` 类型白名单，依据实例 `availability` 与类型目录决定是否可选。

- 默认只展示可用来源，可在“不可用数据源”区域显示当前用户自己的记录及原因。
- 由 `objectSelection` 决定源表/集合/Topic/目录选择器及默认配置键。
- 由 `syncModes` 与任务约束生成策略选项，不再写 `hive/kafka` 特判来禁用增量。
- 不支持的已保存模式显示错误并阻止运行/保存，不静默改为 full。
- 字段读取统一走结构接口；采样字段明确提示采样范围。
- SFTP 结构分类组件仍保留，由 DIRECTORY_RULE 配置选用。

### 10.3 前后端版本不一致

前端加载不到能力目录时，可以继续显示已有列表和历史；新增/编辑/运行入口明确提示重试或更新，不回退到允许全部类型。

短期兼容旧后端如确有发布需要，可保留**单一兼容模块**中的旧目录，并显式标记兼容模式；不能在多个页面重新散落类型判断。最终联调通过后删除兼容模块。

能力目录按登录会话和服务版本缓存；实例能力在数据源新增/编辑、登录切换后刷新。退出必须清除实例缓存。远端对象列表不作为长期能力缓存保存。

## 11. 启动约束与运行时严格性

### 11.1 注册中心启动校验

以下情况启动失败，输出明确的类型与能力名称：

1. 类型标识重复或为空。
2. 对象选择方式与元数据操作不匹配，例如 PICK_ONE 无对象枚举实现，且未明确允许手工输入。
3. 声明同步模式但未绑定执行策略。
4. 对外开放未知的执行策略引用。
5. Kafka/Hive 被错误声明为 incremental，而当前没有对应实现。
6. DIRECTORY_RULE 未绑定目录策略。
7. 必需类/驱动缺失；这里只检查本地依赖，不连远端服务。

不要求 MySQL、Kafka、Hive 在应用启动时全部在线，避免一个离线来源阻断整个平台。Registry 只保存不可变元数据与实现引用，不能保存跨用户连接、Reader 或明文凭据。

### 11.2 保存和运行校验顺序

```text
确认登录/任务所属身份
  → 加载当前用户有权访问的数据源
  → 校验类型/场景/模式及静态配置
  → 校验目标身份与源访问上下文
  → 远端连接、对象、字段及分页条件检查
  → 映射/类型/系统字段/手机号等公共规则
  → 明确读取边界
  → 受控目标建表/补列/清空/批量写入
```

能力检查不能替代数据值检查，也不能承诺所有数据在清表前已完整检查。维持现有阈值/抽样及部分写入语义，并在运行记录中保持明确错误信息；事务化发布属于另一项后续方案。

## 12. 分阶段落地

### 阶段一：先统一声明与判断来源

- 建立注册条目、类型目录、实例可用能力及共享判定器。
- 注册现有全部类型，原样保留新增卡片禁用政策。
- 由现有执行处理器提供一个显式实现目录；每个 `syncBinding` 指向已存在处理器，启动校验交叉检查。此时允许旧引擎内部保留类型分支，不能只检查任意字符串就声称实现已绑定。
- 前端类型选择、同步筛选和模式选项改用服务端能力。
- 保存与运行统一调用能力判定器。

**交付标准：** Kafka/Hive 同类问题不再依赖多份白名单修复；尚未提取 Reader 也可以完成本阶段。

### 阶段二：统一元数据分发

- 将连接测试、对象、字段探测逐源迁入适配器。
- 旧 HTTP 接口作为协议兼容层。
- 专门处理文件权限、SFTP 结构选择和库内 CK 表上下文。

**交付标准：** DataSourceService 不再自行维护各元数据操作的类型支持清单。

### 阶段三：统一读取契约

- 从 SyncEngine 提取 Reader，保留现有 SQL keyset、文件游标、Mongo 游标及精度处理。
- 运行器按执行策略选择 Reader 或目录编排，清除替代完成的类型执行分支。
- 显式 EOF、资源关闭、取消及 Kafka 采样复用完成验收。

**交付标准：** 添加普通来源不需要修改公共 transfer；SFTP 专有业务仍有独立策略。

### 阶段四：清理重复与固化接入规范

- 删除被替代的类型判断和旧兼容目录。
- 更新类型/能力矩阵、适配器说明、接口文档。
- 扫描 UI/Service/Engine 是否还把来源类型作为能力白名单；确属格式或协议特例的判断保留并注释原因。

首轮建议先交付阶段一、二。阶段三范围更大，应独立安排验证，不与增量恢复协议或目标写入重构混在一次发布中。

## 13. 历史兼容、数据变化和回滚

1. 首轮不改 `el_data_sources` 和同步任务表结构，不更新已执行的 SQL 迁移。
2. `type`、源对象、模式、映射、归属记录、加密配置原样保留。
3. 能力是代码实现的描述，不在数据库中新增可随意修改的“支持增量”开关。
4. 当前数据源实例信息不足时，提示补配置；不能自动改绑定用户、目标账号或任务模式。
5. 未来某来源能力被撤回，已有任务可查看，执行明确拒绝；不能默默换执行策略。
6. 按阶段开关切换旧/新分发，**同一请求只走一条链路**。只读能力目录可以做结果比对，不能用双执行方式验证同步任务。
7. 回滚优先回退对应应用及前端版本；由于首轮不改变任务持久化协议，不需要反向迁移业务数据。
8. 正在执行的任务持有创建时的不可变注册与配置快照，更新目录不改变当前读取会话；停机升级按现有运行中任务处理规范执行。

## 14. 验收清单

### 14.1 必须验收的业务场景

| 场景 | 预期结果 |
| --- | --- |
| admin 拥有 Kafka/Hive 数据源 | 同步向导可选择，分别显示 Topic/源表 |
| user 登录 | 只显示该用户有权访问的源；猜测 ID 仍被拒绝 |
| Kafka/Hive 请求 incremental | 页面不允许，直接 API 请求和后台运行也拒绝 |
| MySQL 无可用单列主键 | 类型仍支持同步；具体对象预检明确拒绝，不误写为整个类型不支持 |
| 空 Kafka Topic | Topic 可枚举；字段识别给出明确原因，不生成虚假映射 |
| 新增禁用的 clickhouse/ck_table | 卡片保持禁用；已有授权任务可按原规则使用 |
| 库内 CK 表 | 需目标连接上下文，使用真实用户身份，源等于目标仍拒绝 |
| SFTP 目录 | 目录/模式/结构选择、跳过/重灌/排除/强制重建语义一致 |
| JSON/XLSX 历史任务 | 能查看并按原能力运行，不因卡片隐藏而失效 |
| 手机号明文/MD5 | 明文按现有规则拦截，MD5 按映射规则通过，错误号码仍脱敏 |
| 大整数/Decimal/DateTime64 | 沿用精度范围约束，无 double 中转损失 |
| 调度/XXL-JOB 运行 | 恢复任务用户后执行相同能力校验 |

### 14.2 框架边界验证

- 重复注册、缺少执行器、虚假能力在启动时失败。
- 不足一批但未 EOF 不丢后续记录，空批次处理符合 Reader 契约。
- Reader 异常、取消、超时均关闭资源。
- 新增类型具备一个配置表单、注册条目和执行实现后，无需再修改多个类型白名单。
- GET 类型目录/数据源列表不会触发逐源远端连接。
- 原有数组响应、错误数字 code 以及 SQL 目录包装接口兼容。
- 旧前端/新后端及新前端/旧后端行为有明确发布策略。

验证使用现有 dev 模拟源和临时目标表。按此前项目要求，新增的临时验证代码和临时数据使用后清理，保留模拟源种子文件；原有测试资产按实际变更维护，不擅自删除。

## 15. 首轮完成的判定标准

**不是“新增了 SourceAdapter 接口”就完成。** 必须同时满足：

1. 类型目录由注册中心输出。
2. 前端不再独立声明同步类型和支持模式。
3. 保存与运行调用同一判定器。
4. 声明模式与执行实现存在可验证绑定。
5. 用户归属、真实 CK 身份、文件权限与公共数据校验没有绕开。
6. Hive、Kafka、普通 SQL、SFTP 和历史来源完成对应验收。
7. 接口兼容策略和新类型接入清单已写入文档。
